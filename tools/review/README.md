# 並行レビュー機構

観点ごとに独立したプロセスを**同時に走らせ**、指摘を JSON で吐く。
集約側が指摘を読んで直し、同じレビュアーを再実行する — これを繰り返して
指摘が 0 になるまで回すのが使い方。

## 実行

```
node tools/review/r1-destructive.js <リポジトリのパス>
node tools/review/r2-delete.js      <リポジトリのパス>
node tools/review/r3-render.js      <リポジトリのパス>   # 実ブラウザを使う
node tools/review/r4-ui.js          <リポジトリのパス>   # 実ブラウザを使う
```

4つは互いに独立なので同時に走らせてよい。結果は `tools/review/out/*.json`。

## 観点

| | 見るもの |
|---|---|
| R1 破壊検査 | 更新系が「指定した要素以外」を変えていないか (同じ値で書き戻して不変か) |
| R2 削除検査 | 削除が「押した要素だけ」を消しているか |
| R3 描画整合 | add / connect の結果を mermaid が受け付けるか (実ブラウザ) |
| R4 UI 一貫性 | 全21図種で一覧の ✕ を押し、status が Error にならないか (実ブラウザ) |

## レビュアー自身も間違える

初回は 35件のうち **32件が誤検出**だった。原因はすべてレビュアー側:

- 自動採番 id (`__s_0`) は削除のたびに振り直されるので、id で残存を判定すると
  正しく消えていても「残っている」に見える (R2 で25件)
- `operations.add` の必須プロパティはモジュールごとに違う。id と label しか
  渡さないと出力に `undefined` が混ざり、実装ではなく入力不足で parse が落ちる (R3 で6件)
- requirementDiagram は `name` が図の中での識別子で、`id` は要件番号という
  別の値。id を使うと存在しない端点で関係を作る (R3 で1件)

**指摘が出たらまず「レビュアーが正しいか」を実機で確かめること。**
誤検出を実装の欠陥として直すと、動いていたものを壊す。
