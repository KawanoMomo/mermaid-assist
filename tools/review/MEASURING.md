# 測るときの規約

**なぜ書くか**: ラウンド66 の1ラウンドだけで、**測る対象を4回間違えた**。
うち1回は Blocker 級の誤報を出す寸前だった。原因はすべて同じなので規約にする。

## 何が起きたか

| # | 何を測ったつもりか | 実際に測っていたもの | 危うく出しかけた結論 |
|---|---|---|---|
| 1 | 一覧の要素名 | 副次ラベル `(N0, rect)` | 「名前は切れていない」(見逃し) |
| 2 | 図がスクロールできるか | `#preview-pane` (外枠。スクロールするのは `#preview-container`) | 「縦長の図の下側に到達できない」(**誤報寸前**) |
| 3 | ヘルプに複数選択の記載があるか | 折りたたまれた要素の `innerText` (空になる) | 「ヘルプに記載が無い」 |
| 4 | 途中挿入・並べ替えの経路 | 一覧行のボタンだけ (実際は詳細パネルにある) | 「経路が無い」 |

**共通する原因**: セレクタを推測で書き、**取れた値がもっともらしいと、
取る対象が正しいかを確かめずに先へ進んだ**。

これは C78 (自分が書いた属性を読み返して「改善した」と主張した) と同じ形。

## 規約

### 1. 数値を出す前に、対象の `outerHTML` を1回出す

```js
console.log(el.outerHTML.slice(0, 400));   // これを見てから測る
```

セレクタが合っているかは、値ではなく**構造**を見ないと分からない。

### 2. 「〜できない」という否定形の結論は、二重に確かめる

否定は「見つからなかった」と区別が付かない。書く前に:

- 根拠になった要素が**本当にその役割を持つ要素か**を確かめる
- **別の場所に同じ機能が無いか**を探す (一覧に無くても詳細パネルにあった)
- 実装側を `grep` して、**その機能の存在を示す語**が無いかを見る
  (`insertBefore` を grep していれば4番目の誤りは起きなかった)

### 3. 隠れている要素は `innerText` で測らない

`display:none` の子孫は `innerText` に出ない。**開いてから測る**か、
`textContent` を使う。3番目の誤りはこれ。

### 4. 契約 (operations) を呼ぶ前に、実装の署名を読む

推測で `operations.add(text, {label})` と書いて 0行 diff という**嘘の結果**を
出した。実際は `add(text, kind, props)`。**規約は実装を読んで確かめる。**

### 5. SVG の中身は `textContent` を丸ごと取らない

`<style>` ブロックが混ざって数千文字になり、肝心のラベルが埋もれる。
見たいものだけ取る:

```js
Array.from(document.querySelectorAll('#preview-svg svg .nodeLabel'))
  .map((n) => (n.textContent || '').trim())
```

### 6. 生死の監視に CPU 時間だけを使わない

待ち時間主体のテスト (`waitForTimeout` が多い) では CPU がほとんど進まず、
**ハングと区別が付かない**。`test-results/` 配下の更新時刻を併用する。

### 7. 変化そのものを差分で取る (推測したセレクタで探さない)

R66 で「一覧で選んでも図で光らない」と**2回結論しかけた**。実際は光っており、
強調は**クラス名ではなく `stroke` 属性**で表現されていた。クラス名で探していた。

決着したのは、選択の前後で `preview-pane` の `innerHTML` を丸ごと差分し、
**変わった3文字**を見たとき。

```js
const before = await snap();   // innerHTML
/* 操作 */
const after = await snap();
// 一致しない位置を探して、その周辺を出す
```

推測したセレクタは「無い」と「見つけられない」を区別できない。**差分は区別できる。**

### 8. 変異が挙動を変えないなら、そのコードは効いていない

R66 で「同じ選択なら動かさない」ガードを書いたが、**変異を入れても挙動が
変わらなかった**。調べると、打鍵の描画経路 (`app.js:413`) はそもそもその関数を
通らず、ガードは死んだコードだった。

**効かないコードに「〜を守っている」と注釈を書くと、嘘が資産として残る。**
変異で落ちないコードは、消すか、効く場所へ動かす。

### 9. 変異が落ちないときは、変異とテスト条件の**両方**を疑う

規約8の裏。変異を入れても落ちないとき、原因は2通りある:

- **コードが効いていない** (規約8) → 消すか、効く場所へ動かす
- **テストの条件が甘い** → 守りたい性質が再現していない

R68 で後者を2回踏んだ。幅の制限を外す変異が落ちず、原因は
「既定の短い名前で測っていた」ことだった。名前を伸ばしても足りず、
**実務で起きる長さ**にして初めて落ちた。

条件を推測で決めると、**通るテストが1つ増えるだけ**になる。
守りたい性質を1文で書き、その性質が壊れる条件を実測で探す。

### 10. alert を自動承認したまま「黙っている」と言わない

**最も長く気付かなかった穴。**

測定コードは常に `page.on('dialog', d => d.accept())` を書いていた。
ダイアログが操作を止めるのを避けるためだが、**alert によるフィードバックを
すべて潰していた**。

R70 で「本文が空のとき追加を押しても何も言わない」(UI-079) を報告したが、
**実際は `alert('IDは必須です')` が出ていた**。しかも原因も違った —
本文が空かどうかは無関係で、**ID欄が空だと追加できない**のが真の挙動だった
(本文空 + ID="X" では +9文字で足せる)。

`alert(` は **10モジュール以上**で使われている
(architecture 3 / block 4 / c4 3 / class 4 / er 3 / flowchart 3 / …)。
**「黙って失敗する」系の指摘は、alert を記録していない測定では出せない。**

```js
const dialogs = [];
p.on('dialog', (d) => { dialogs.push(d.type() + ': ' + d.message()); d.accept(); });
```

承認するのは同じでも、**文言を残す**。残していれば UI-079 は出さずに済んだ。

### 11. 合否は**終了コード**で見る。出力の最後の行で見ない

UI-083 の変異検査で、3件すべてを「落ちない (検査が弱い)」と誤って報告した。
原因は判定の書き方:

```python
t = [l for l in out.splitlines() if 'passed' in l or 'failed' in l]
fell = 'failed' in t[-1]        # ← 最後の行だけ見る
```

Playwright は失敗と成功を**別の行**に出す:

```
  1 failed
  2 passed (16.7s)
```

`t[-1]` は `2 passed` を拾うので、**1件落ちていても「落ちなかった」と読む**。
実際は `exit=1` で、変異はすべて正しく検出できていた。

判定は必ず `returncode` で行う。件数の行は**人が読むための添え物**であって、
判定の根拠にしてはいけない。

これは検査器で3回・棚卸しで1回出た「失敗が見えない書き方」と同じ型で、
**測る側の道具でも起きる**。SILENT ゲートは `tools/review/` しか見ないので、
その場限りの測定スクリプトはこの規約でしか守れない。

## 効いた例

4番目の誤りに気付いて実UIを操作し直したことで、**UI-072 (Major) に辿り着いた**。
誤りの過程が無駄だったわけではないが、**規約があれば最初から辿り着けた**。
