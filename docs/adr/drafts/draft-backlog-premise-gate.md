# (ドラフト) 先送りした項目は「前提」を機械に見張らせる

- **ステータス**: ドラフト (未採番・未登録)
- **カテゴリ**: プロセス
- **日付**: 2026-08-22
- **対象プロジェクト**: MermaidAssist (他プロジェクトへ横展開可能)
- **関連ADR**: なし

## なぜ起票するか

棚卸しの運用そのものを変えた。**他プロジェクトにも同じ穴がある**ため、
横展開の判断材料として残す。

## 何が起きていたか

バックログの項目には「復活条件」を書く運用にしていた。
しかし**条件が満たされたことを誰も監視していなかった。**

    G4 の復活条件: 「契約経由で `add` を呼ぶ経路を作る時点」
    → その経路は6ラウンド後に**私自身が作っていた**。
      気付いたのは、無関係な未確認事項を追いかけた偶然だった。

## 決めたこと

**復活条件ではなく「前提」を見張る。**

復活条件は人の決定を含むことが多く (「訳す範囲を決めた時点」)、機械化できない。
一方、先送りしてよい**理由 (前提)** はコードの状態であることが多い。

| 項目 | 前提 | 見張り方 |
|---|---|---|
| G1 | class/er/state が `move: false` のまま | grep |
| G6 | 一覧に仮想化が無い | grep |
| G2/G3/G5/G7/G8 | 人が決めるまで動かない | **[人の判断待ち] と宣言させる** |

**宣言の無い項目を足すと FAIL する。** これで「また誰も見張らない項目ができる」
のを止める。削除リスト (H区分) も同様に見張り、**復活条件が空なら FAIL** する。

## 併せて決めたこと: 滞留には期限を切る

同じ質問を22回繰り返すのは PL の仕事ではない。**既定動作と期限を予告し、
回答が無ければ実行する** (凍結して削除リストへ移す)。

**凍結は「捨てる」ことではない。** 戻ってくる経路を機械に持たせて初めて、
凍結と放置が区別できる。

## 実装上の注意 (実測で判明)

**復活の合図は「置かれる場所」で判定する。** 資料の末尾に
「案を選ぶときはこう書いてください」という再開手順を書いたところ、
その**例文**を「案が選ばれた」と誤検出した。**指示と決定は見た目が同じ。**
行頭に置かれたものだけを決定とみなす。

## 影響

- ゲートが9 → **10項目** (`PREMISE` を追加)
- ゲートの3項目 (DOC / REC / PREMISE) は**成果物ではなく棚卸しを検査する**
- 変異3種で確認 (前提が崩れる / 一覧に上限が入る / 宣言の無い項目を足す)
