# (ドラフト) 描き直しの待ち時間は「前回かかった時間」から決める

- **ステータス**: ドラフト (未採番・未登録)
- **カテゴリ**: 性能
- **日付**: 2026-08-22
- **対象プロジェクト**: MermaidAssist
- **関連ADR**: なし

## なぜ起票するか

固定値の待ち時間を選ばなかった理由が、コードのコメントにしか無い。
「150ms 以下が好み」という一般的な指針と食い違う判断なので、根拠を残す。

## 何が起きていたか (実測、1366x768)

`scheduleRefresh` は `requestAnimationFrame` で合流させていたが、
**同じフレームの中しかまとめない**。人が打つ速さ (毎秒5文字 = 200ms 間隔) では
合流せず、1打鍵ごとに図全体を描き直していた。

10文字打つ間に UI が固まった合計 (ページ内の rAF でフレームの途切れを計測):

| 要素 | 前 | 後 |
|---|---|---|
| 10 | 0ms | 0ms |
| 50 | 797ms (10回) | 789ms (10回) |
| 200 | **4988ms (10回)** | **524ms (1回)** |
| 400 | **14718ms (10回)** | **1409ms (1回)** |

## 検討した案

| 案 | 判断 |
|---|---|
| A | 固定 150ms | **却下 (実測)**。200ms 間隔の打鍵に**1回も合流しない**。効果ゼロ |
| B | 固定 400〜800ms | 却下。軽い図で無駄に遅くなる。50要素は描き直しが80msで、待つ理由が無い |
| C | **前回の描き直しにかかった時間から決める** (150ms 以下なら待たない、上限800ms) | **採用** |
| D | 読み取りと状態表示だけ先に走らせる | **却下 (実測)**。合計が 1460ms → **22194ms に悪化**。一覧の作り直しが400要素で1打鍵あたり約850ms かかるため |

## 決めたこと

    function refreshDelay() {
      if (lastRenderMs <= 150) return 0;              // 軽い図はそのまま
      return Math.min(Math.round(lastRenderMs), 800); // 重い図は前回かかった分だけ待つ
    }

**「150ms 以下は遅く感じる」という指針と矛盾しない。** 軽い図では待ち時間が
0 のままで、待つのは1回の描き直しが150msを超える図だけ。そこでは
「待たない = 1.5秒固まる」なので、待つほうが速い。

## 影響

- 状態表示が最大800ms遅れる (承知の上。案Dが悪化したため)
- 大きい図では描画前に「描画中 …」を出す (塗ってから重い処理へ入る)
- `tests/e2e/typing-freeze.spec.js` が固定。変異 (待ち時間を常に0) で1件落ちる
