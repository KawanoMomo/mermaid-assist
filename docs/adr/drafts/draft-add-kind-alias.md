# (ドラフト) `operations.add` は `parse` が返す kind を別名として受ける

- **ステータス**: ドラフト (未採番・未登録)
- **カテゴリ**: インターフェース
- **日付**: 2026-08-22
- **対象プロジェクト**: MermaidAssist
- **関連ADR**: ADR-012 (DiagramModule v2)

## なぜ起票するか

ADR-012 の契約 `operations.add(text, kind, props)` に、
**kind がどこから来る値なのか**が書かれていない。そのずれで2図種が
契約経由で足せなくなっていた。契約の解釈を決めた記録を残す。

## 何が起きていたか (実測)

`parse` が返す `element.kind` と `add` が受ける kind が一致していなかった。

| 図種 | 一覧に出る kind | add が受ける kind |
|---|---|---|
| mindmap | `node` | `child` / `sibling` |
| sankeyBeta | `node` | `flow` |

一覧に出ている種類で足せないので、契約経由の呼び出しは**黙って空振り**する。

**6ラウンド前に G4 として「実害が無い」と判断して先送りしていた。**
復活条件は「契約経由で `add` を呼ぶ経路を作る時点」。
その経路は、**前ラウンドで私自身が r8 を書き換えたときに作っていた** —
気付いたのは無関係な未確認事項を追いかけた偶然だった。

## 検討した案

| 案 | 判断 |
|---|---|
| A | `parse` の kind を `child` / `flow` に合わせる | 却下。一覧の表示が変わり、既存の選択・削除の照合も壊れる |
| B | `add` の kind を `node` に統一する | 却下。mindmap は子と兄弟を撃ち分ける必要があり、情報が落ちる |
| C | **`add` が一覧の kind を別名として受ける** | **採用**。既存の呼び出しを一切変えない |
| D | 契約に「kind は parse が返すもの」と書いて全図種を直す | 将来案。今回は影響範囲が読めない |

## 決めたこと

**`operations.add` は、少なくとも `parse` が返す `element.kind` を受け付ける。**
図種固有の細かい種類 (`child` / `sibling` / `flow`) は追加で受けてよい。

    mindmap  kind='node' → 親を指定していなければ根の子として足す
    sankey   kind='node' → 既存のノードからの流れを1本足す
                           (ノードは流れの端点としてしか存在しない)

## 影響

- `tests/contract-add-kind.test.js` が21図種で「一覧の種類で足せる」を固定
- `tools/review/r8-scale.js` の網羅が 19 → **21/21**
- 契約経由で文書を育てられるようになった (検査が100要素まで育てて測れる)

## 未解決

- 案D (契約に明記して全図種を揃える) は未着手。
  **kind の名前を揃えるかどうかは ADR-012 の改訂**になるため
