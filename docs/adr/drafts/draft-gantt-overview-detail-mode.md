- **ステータス**: **ドラフト (未採番・未承認)**

- **日付**: 2026-08-19
- **対象プロジェクト**: MermaidAssist
- **関連ADR**: 横断 ADR-010 (日付⇔ピクセル変換)、MA ADR-011 (JS外部分割)
- **関連spec**: `docs/superpowers/specs/2026-08-18-gantt-ui-improvements-design.md`

## コンテキスト

Gantt のプレビューが読めない。実測 (Chromium、コンテナ幅 890px、4タスク):

| 項目 | 実測値 |
|---|---|
| mermaid が出力する SVG | `viewBox="0 0 1600 196"` |
| auto-fit ズーム | 54% |
| タスク文字 | 11px → **実効 5.9px** |

`mermaid.initialize` に gantt 設定が無い (`src/app.js:1050-1054`) ため mermaid 内部
デフォルトの `useWidth: 1600` が適用され、内容が 4 タスクしかなくても SVG は常に
横 1600px のキャンバスに引き伸ばされる。一方フォントは 11px 固定。現行の auto-fit は
CSS `transform: scale()` で**文字ごと縮めている**ため、全体を収めると文字が読めず、
文字を読もうと拡大するとバーが巨大化して全体が入らない。

## 検討した選択肢

### A) フォントとバー高さを拡大して fit ズームに耐えさせる

- メリット: 変更が小さい
- デメリット: タスク数が増えれば同じ問題が縦方向で再発する。根本解決にならない

### B) `gantt.useWidth` で描画そのものを制御し、2 モードを持つ

- 概観 = `useWidth` をコンテナ幅、詳細 = `useWidth` を `日数 × px/日`
- メリット: フォントは常に 11px のまま。「読める」が構造的に保証される
- デメリット: `mermaid.initialize` の再実行が必要で、その副作用を扱う必要がある

### C) 常に概観 (コンテナ幅固定) にし、拡大は従来の CSS zoom

- メリット: 最小実装
- デメリット: 拡大時に文字も一緒に大きくなるので、細部を見ながら全体を把握できない

## 決定 (案)

**B) 2 モード + `useWidth` 制御**を採用する。切替 UI は新規追加せず、**既存の
`btn-zoom-fit` を再定義**する (fit 押下=概観、`±` 操作で詳細へ自動復帰)。
再定義は `currentModule.type === 'gantt'` でガードし、他 20 図種の従来挙動を維持する。

**あわせて mermaid config の投入経路を 1 箇所に集約する。**

実測で判明した重要な性質: **`mermaid.initialize` はマージではなく置換**である。

| 操作 | viewBox | バー色 |
|---|---|---|
| アプリ既定 (`theme: dark`) | 997 | `rgb(89,92,92)` |
| `{gantt:{useWidth:880}}` のみ渡す | 880 | **`rgb(138,144,221)`** (テーマが飛ぶ) |
| `{startOnLoad,theme,securityLevel}` のみ渡す | **997** (useWidth 消滅) | `rgb(89,92,92)` |

部分オブジェクトを渡すと `theme` dark→default、`securityLevel` loose→strict、
`startOnLoad` false→true になる。したがって:

- **全設定を組み立てて渡す単一関数 `applyMermaidConfig({...})` を作り、
  `mermaid.initialize` の呼び出しをその 1 箇所に限定する**
- **モード状態はアプリ側の変数を真とし、mermaid の config はその派生物**とする。
  config にしかモード状態が無いと、将来 `initialize` を呼ぶコードが 1 箇所増える
  だけでモードが無言で失われる
- 詳細モードの `useWidth` はテキスト編集のたびに変わるため、**描画パイプラインの
  先頭で常に config を再構成する**ことを `refresh()` の責務とする

## 教訓 (現時点で確定しているもの)

1. **ライブラリの設定 API がマージか置換かを実測で確かめる。** ドキュメントの語感で
   マージだと思い込むと、部分指定が他の設定を黙って壊す。
2. **状態の真の置き場所を 1 つに決める。** 外部ライブラリの config を状態の保持先に
   すると、そのライブラリを触る別経路が増えた瞬間に状態が失われる。
3. **「fit」のような既存 UI の意味を変えるときは、影響範囲を型で絞る。** 全図種共有の
   ボタンを再定義するなら図種ガードが要る。
