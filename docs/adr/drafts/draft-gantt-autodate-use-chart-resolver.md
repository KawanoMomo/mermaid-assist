# ADR-NNN: ガントの日程自動送りを、チャートと同じ解決器で行う

- **ステータス**: 提案（未採番）
- **カテゴリ**: (categories.md から選択 — 「述語の一本化」系)
- **日付**: 2026-08-23
- **対象プロジェクト**: 05_MermaidAssist
- **関連ADR**: ADR-024 (較正入力の健全性), ADR-025 (概観/詳細モード)

## コンテキスト

タスク追加フォームは「前タスクの終了日を次の開始日に自動で送る」既定値を出す。
その実装 `nextStartDate` / `nextDurationDays` は、パーサが持っている生のトークンを
見て `DATE_RE`（`\d{4}-\d{2}-\d{2}`）に合わなければ `null` を返していた。

この方針はテストにも明記されていた:

> AT-8: 終了日が duration なら null
> 「解決値を推測して静かに誤った日付を入れるより、空で出す」

ところが gantt のパーサは第2トークンをそのまま `endDate` に入れる。つまり

- 期間指定 `設計 :t1, 2026-03-01, 5d` → `endDate = '5d'`
- `after` 連鎖 `実装 :t2, after t1, 5d` → `startDate = 'after t1'`
- マイルストーン `DR1 :milestone, m1, 2026-03-20, 0d` → `endDate = '0d'`

のいずれもここで弾かれる。**期間指定は最も普通の書き方**であり、**マイルストーンは
構文上かならず `0d` を持つ**（無いと mermaid がチャートから落とす）。

実務ユーザー観点の実機レビューで、この方針は次の形で現れた:

> マイルストーンを1本追加すると日付欄が空になり、「タスク」に戻しても空のまま。
> 以後の追加は全部「開始日を入れてください」で弾かれ、日付を手打ちするまで
> 復帰しない。

つまり「安全側に倒す」つもりの `null` が、**追加フォームを使用不能にする**という形で
表に出ていた。

## 検討した選択肢

### A) 現状維持（解決できない形は `null`）
- 概要: 明示的な日付が両端にあるときだけ送る。
- メリット: 誤った日付を静かに入れる余地がゼロ。
- デメリット: 期間指定・`after`・マイルストーンという**実務で普通の3形**すべてで
  フォームが機能しない。マイルストーンを1本置いた時点で以後の追加が全滅する。
  「安全」の代償が大きすぎる。

### B) 自動送り用に日付解決のロジックを新しく書く
- 概要: `nextStartDate` の中で `Nd` を解いて加算する。
- メリット: 変更範囲が小さい。
- デメリット: **チャートを描く `resolveSpan` と別の解決器が2本になる**。
  block の無名グループ / c4 の素の Boundary で実際に起きた「述語の非対称」を
  自分から作りに行くことになる。ずれた瞬間、図に描かれている終わりの日と
  フォームが提案する開始日が食い違い、しかも誰も気づけない。

### C) チャートと同じ `resolveSpan` を使う（採用）
- 概要: `resolveSpan` は既に期間・`after` 連鎖・アンカー無しの継続を解いている
  （これがチャートの描画そのもの）。各タスクの解決後の終了日を返すようにして、
  自動送りはそこから取る。
- メリット:
  - 提案する日付が、**画面のチャートに実際に描かれている終わりの日と必ず一致する**。
  - 「推測」ではなくなる。A の前提（＝推測を避ける）は、別の手段で満たされる。
  - 解決器が1本のまま。ずれようがない。
- デメリット:
  - `resolveSpan` の解釈が mermaid の解釈と違えば、フォームも一緒に間違える。
    ただしその場合チャートも同じく間違っているので、**画面を見れば分かる**
    （既定値は送信前に日付欄に表示され、利用者が上書きできる）。

## 決定

**C を採用する。** A の「推測して静かに誤った日付を入れない」という意図は正しいが、
その手段として「解決できるものまで捨てる」を選んだのが誤りだった。同じ意図は
「チャートと同じ解決器を使う（＝推測しない）」で満たせる。

あわせて、期間の既定値はマイルストーンから取らない。マイルストーンは点なので長さが
0 であり、それを次の既定にすると「開始日 = 終了日」の空タスクが提案される。
直前の通常タスクの長さを引き継ぐ。

## 結果

- `resolveSpan` に `endsByIndex`（タスク index → 解決後の終了日）を追加し、
  `lastResolvedTask` / `nextDurationDays` をそこから引くようにした
- 既存テスト AT-8 / AT-9 / AT-15 は旧方針を固定していたので、前提の変更を
  コメントに明記したうえで期待値を更新した
- 実測:

  | 直前のタスクの形 | 修正前 | 修正後 |
  |---|---|---|
  | `2026-03-01, 5d`（期間指定） | null | **2026-03-06 / 5日** |
  | `after t1, 2026-03-20` | null | **2026-03-20** |
  | `:milestone, 2026-03-20, 0d` | null | **2026-03-20 / 直前の通常タスクの日数** |
  | マイルストーンのみ | null | 2026-03-20 / **期間は null**（点から長さを取らない） |

- 残課題: 日付欄には `min` / `max` が無く、年に「26」や「0620」を打つと
  `0026-05-30` / `62020-02-06` が無警告で通る（parse は OK のまま）。
  これは本 ADR の範囲外だが、同じ「追加フォームが黙って死ぬ」系の課題として
  別途対応する
