# Gantt UI 改善: 概観/詳細モード・セクション移動・連続入力・マイルストーン

**日付**: 2026-08-18
**状態**: 設計確定、実装計画へ
**関連**: MA ADR-018 (モジュールレジストリ merge)、横断 ADR-010 (日付⇔ピクセル変換)、横断 ADR-008 (SVGオーバーレイ)

## 背景

実機 (`localhost:8765`) で Gantt を操作した結果、5 件の課題が挙がった。いずれも
Tier1〜Tier3 で 21 図種へ横展開を進める過程で、**Gantt だけが取り残された**こと
に起因する。Gantt は最初期に `src/app.js` へ inline 実装され、その後に整備された
共通ヘルパ (`window.MA.properties.*`)・ctx 契約・アクションバー規約のいずれにも
乗っていない。

本 spec は 5 件の要件を定義するとともに、その前提として MA ADR-018 が
「Tier3 完了後のリファクタ候補」と予約した **inline gantt の完全移行**を先に
消化する方針を確定する。

## 現状の実測値

計測環境: Chromium、ビューポート 1600x1000、プレビューコンテナ幅 890px、
デフォルトの Gantt サンプル (4 タスク / 2 セクション)。

| 項目 | 実測値 |
|---|---|
| mermaid が出力する SVG | `viewBox="0 0 1600 196"` / `width="1600"` |
| プレビューコンテナ幅 | 890px |
| 適用される auto-fit ズーム | **54%** |
| タスク文字 | 11px → **実効 5.9px** |
| バー高さ / 幅 | 20px / 461px (2週間タスク) |
| `mermaid.initialize` の gantt 設定 | **なし** (`src/app.js:1050-1054`) |

`useWidth` を指定していないため mermaid 内部デフォルトの 1600 が適用され、
内容が 4 タスクしかなくても SVG は常に横 1600px のキャンバスに引き伸ばされる。
一方フォントは 11px 固定。結果として「バーだけが横に肥大し、文字は固定サイズ」
という比率の不整合が生じ、全体を収めようと縮めると文字が読めず、文字を読もうと
拡大するとバーが巨大化して全体が入らない。

### スパイク結果 (実機検証済み)

`mermaid.initialize({gantt:{useWidth:N}})` + 再描画による制御可否を実機で検証した。

| useWidth | viewBox | SVG の `width` 属性 | バー幅 | フォント |
|---|---|---|---|---|
| 未指定 (現状) | `0 0 1600 196` | `1600` | 461px | 11px |
| 880 | `0 0 880 196` | **`100%`** | 232px | 11px |
| 2400 | `0 0 2400 196` | **`100%`** | 716px | 11px |

- `useWidth` の再指定は繰り返し有効 (one-shot ではない)
- フォントは常に 11px、バー幅だけが `useWidth` に比例する
- **`useWidth` を明示すると mermaid は `width` 属性を `100%` で出力する**

最後の点は実装上の分岐に**ならない**。既存の描画パイプライン (`src/app.js:840-849`)
が毎回 `svgEl.removeAttribute('style')` でインラインスタイルを捨て、viewBox 幅を
そのままピクセル値として `width` / `height` に設定し直し、overlay も同じ viewBox に
同期しているためである。`useWidth` を指定して得た `width="100%"` はこの時点で
上書きされる。実測で確認済み (下記)。

### スパイク結果 2: 座標系とドラッグ操作 (実機検証済み)

`useWidth = 436` (コンテナ幅) に再初期化してアプリ本体の描画を走らせた実測値:

| 項目 | 実測 |
|---|---|
| SVG の `width` 属性 | `436` (`100%` ではない) |
| SVG のインラインスタイル | 除去済み (`null`) |
| preview と overlay の viewBox | 完全一致 (`0 0 436 196`) |
| 較正側 `getBBox()` と ドラッグ側 `getScreenCTM().inverse()` の X 差 | **0** |

**横断 ADR-010 (日付⇔ピクセル変換) は `useWidth` 変更で壊れない。** ただし理由は
本 spec が当初書いていた「較正が描画毎に再計算されるから」ではない。正しくは、
パイプラインが `width="100%"` をピクセル値へ正規化し overlay の viewBox を同期する
ため、`calibrateScale` が使う `getBBox()` (viewBox 座標) と、ドラッグが使う
`getScreenCTM().inverse()` (画面→viewBox 変換) が同じ座標系に揃うからである。

### スパイク結果 3: モード切替時のズームリセット (必須)

`useWidth` を変えただけでは**それ以前のズーム倍率が残り、CSS transform で二重に
縮小される**。実測では `useWidth` をコンテナ幅に変えた直後もズーム表示が 44% の
ままで、コンテナ幅ぴったりに描画したはずの図がさらに 44% に縮んだ。auto-fit は
初回描画時 (`thisRender === 1`) にしか走らないためである。

**モード切替時は `useWidth` の変更と同時に `setZoom(1.0)` を行うこと。** これを
落とすと、概観モードが「全期間が収まる」どころか従来より小さく表示される。

## 設計方針: ADR-018 C の消化を先行する

### 決定

機能追加 (項目 2 / 3 / 5) に着手する前に、**inline gantt の renderProps を
`src/modules/gantt.js` へ完全移行する**。移行は機能追加を一切含まない
「振る舞い不変」のコミットとして独立させる。

### 根拠

1. **今回の 5 項目のうち 3 つが移行対象コードそのもの**。セクション一覧・追加
   フォーム・詳細パネルはすべて inline renderProps (`src/app.js:200-758`、約
   560 行) の中にある。先に機能を書けば約 200 行を「これから消す場所」に足し、
   後日の移行で同じコードを再度触ることになる。GUI 変更には実機スクリーン
   ショット検証が必須なため、検証コストも二重に払うことになる。

2. **inline 経路には既知バグの修正が入っていない**。`ctx.setMmdText`
   (`src/app.js:924-937`) には同期 re-parse 修正 (commit `a4e8410`) が入って
   おり、コメントに症状が明記されている ―「*module-level `parsed` stayed stale
   until the async refresh tick and caused selection look-ups to hit wrong
   messages (visible as「上下を押すと選択が入れ替わる」)*」。しかし直前の
   `if (currentModule.type === 'gantt')` 分岐 (`src/app.js:919-921`) により
   **Gantt だけが 2 引数形式でこの ctx を通らない**。inline のハンドラは
   `mmdText` を直接代入するのみ (`src/app.js:452-460`)。

   項目 2 (セクション上下移動) と項目 3 (追加 → 即再描画 → フォーカス復帰) は、
   まさにこの stale-parse バグが再発する操作形状である。移行せずに進めると
   「同じ修正を inline 側に二重実装する」か「既知バグを再導入する」かの二択になる。

3. **据え置きの根拠が事実誤認だった**。MA ADR-018 は「inline gantt は
   `src/app.js` の内部関数 (calibrateScale 等) と密結合」としているが、実際は
   逆で、`calibrateScale` を含む 24 個の関数は `src/modules/gantt.js` から
   import されている (`src/app.js:4-22`)。parse/update ロジックは既に外部に
   あり、inline に残っているのは実質 renderProps とそのハンドラのみ。移行の
   技術的障壁は ADR 起票時の想定より大幅に低い。

4. **構造上の特例が 3 つ消える**: (a) renderProps ディスパッチャの
   `if (currentModule.type === 'gantt')` 2 引数特例、(b) ADR-018 のレジストリ
   merge が Gantt にだけ必要という状態、(c) 21 図種中 Gantt だけが
   `window.MA.properties.*` ヘルパー非使用。

5. **安全網が揃っている**。`src/modules/gantt.js` のロジックは移行で不変なので
   既存ユニットテストがそのまま回帰検出に使える。`tests/e2e/gantt-basic.spec.js`
   も存在する。移行コミットは振る舞い不変なので before/after スクリーン
   ショット一致を機械的な合格条件にできる。

### 却下した案

- **A) 機能追加のみ、リファクタは分離**: 根拠 1・2 の二重コストとバグ再導入
  リスク。加えて ADR-018 が明記した消化時期を黙って先送りすることになり、
  「承認済み ADR と矛盾する進行はドラフト起票なしに進めない」という運用ルール上、
  先送り自体の ADR 追記が必要になる。速く見えて手戻りが最大。
- **C) 今回触る部分だけ外部へ切り出す**: 切り出したヘルパが inline のグローバル
  (`mmdText` / `editorEl` / `suppressSync`) と ctx 契約のどちらに依存するかを
  決める必要がある。擬似 ctx を作るなら移行の大半をやるのと変わらず、作らない
  なら inline / 外部に次ぐ「第 3 の構造」が増え、後日の完全移行でヘルパを再度
  書き直すことになる。根拠 2 の stale-parse 問題も解決しない。

### 移行時の必須条件

**inline 定義の削除と外部側の追加は同一コミットで行う。** ADR-018 のレジストリ
merge は「欠落プロパティのみ補完・既存は上書きしない」実装のため、inline
renderProps が 1 行でも残ると外部側 renderProps は永遠に呼ばれず、古い UI が
無言で表示され続ける (shadowing)。中途半端な移行が最も危険。

## 機能設計

### 項目 1: 概観モード / 詳細モード

**課題**: 現行の auto-fit は CSS `transform: scale()` で **文字ごと縮めている**
(`src/app.js:862-869`)。そのため全体を収めると文字が読めない。

**設計**: 2 モードを導入し、`useWidth` で描画そのものを制御する。

| モード | `useWidth` | SVG `width` 属性 | ズーム | 結果 |
|---|---|---|---|---|
| 概観 | コンテナ幅 | `100%` のまま | 100% | 全期間が横に収まり、文字は 11px を維持 |
| 詳細 | `max(コンテナ幅, 日数 × DETAIL_PX_PER_DAY)` | ピクセル値へ上書き | 100% | 横スクロールで全期間を辿る |

`DETAIL_PX_PER_DAY` は名前付き定数とし、**初期値 24px/日**とする (1 ヶ月 ≈ 720px、
1 年 ≈ 8760px)。この値は理論的に導けるものではないため、実機スクリーンショット
検証で「タスク名と日付軸ラベルが潰れない最小密度」を確認して調整する。調整結果は
実装計画に記録する。

概観モードには最小バー幅を設けない。長期プロジェクトではバーが細くなるが、それは
「全期間が収まる」ことの対価であり、細部を見るための手段が詳細モードである。

**縦方向**: 横だけ収め、縦はスクロールとする。バー高さ (20px) とフォント (11px)
は**常に固定**。タスク数に応じて縦を圧縮する案は採らない ― それは今回直そうと
している「文字が潰れる」問題を縦方向で再発させるため。

**切替 UI**: 新規 UI を追加せず、**既存の `btn-zoom-fit` を再定義する**。

```
通常時:  [−] [ 100% ] [+] [ fit ]
                            ↑ 押下で概観モードへ

概観中:  [−] [ 概観 ] [+] [ fit ]
               ↑ ± を押すと詳細モードへ復帰
```

`zoom-display` にモード名を出すことで、現在どちらにいるかを既存の表示領域だけで
伝える。状態は「概観 / 詳細」の 2 値と `zoom` 倍率の組で持つ小さな状態機械として
明文化する。

**他図種への波及防止**: `btn-zoom-fit` はすべての図種で共有されている。Gantt 以外
の 20 図種では mermaid が内容に合わせて SVG サイズを決めるため、従来の
CSS スケール方式の `zoomToFit` が正しい。したがって**再定義は
`currentModule.type === 'gantt'` でガードする**。

**`useWidth` の注入方法**: モード切替ごとに `mermaid.initialize` を再実行する
(スパイクで再実行が有効であることを確認済み)。ユーザーのテキストへ directive を
書き込む方式は、ソースオブトゥルースを汚染するため採らない。

**ADR-010 との関係**: 実機検証済み (スパイク結果 2)。`useWidth` を変えても
較正側とドラッグ側は同じ座標系に揃うため、バーのドラッグ操作は壊れない。ただし
検証したのは座標変換の一致までで、「モード切替 → 実際にバーをドラッグ → 書き戻された
日付が正しい」までの通し操作は未実施。実装時に実機で確認する。

### 項目 2: セクションの上下入れ替え

**課題**: セクション一覧の各行 (`src/app.js:224-229`) には `✕` 削除ボタンしか
なく、順序を変える手段が UI 上に存在しない。タスク側には `prop-move-up` /
`prop-move-down` (`src/app.js:449-450`、`moveTaskWithinSection`) がある。

**設計**: セクション一覧の各行に ↑ ↓ を追加し、タスク側と対称にする。
**セクションの移動は配下タスクを伴う** (セクションはその範囲のタスクを所有する)。
`src/modules/gantt.js` に `moveSection(text, sectionIndex, direction)` を追加し、
セクション見出し行から次のセクション見出し行の直前までを 1 ブロックとして
入れ替える。先頭/末尾での移動は no-op (テキスト不変) とする。

### 項目 3: タスクの連続入力

**課題**: `propsEl.innerHTML = ...` によるパネル全面再構築でフォーカスが消失する。
Enter キーでの追加バインドもない。複数タスクを連続投入するたびにマウス操作が要る。

**設計**:

- 追加フォームのいずれのフィールドでも **Enter で追加を実行**する
- 追加後、**ラベル欄へフォーカスを戻し、テキストを全選択**する
- **日程を自動送りする**: 次の開始日 = 前タスクの終了日。期間 (日数) は直前の
  タスクと同じ日数を維持する

```
1件目: 要件分析  2026-04-01 → 2026-04-15   (14日)
2件目: (自動)    2026-04-15 → 2026-04-29   (14日を維持)
3件目: (自動)    2026-04-29 → 2026-05-13
```

ラベルを打って Enter、の繰り返しで逐次工程が連なる。並行工程のときだけ日付を直す。

- **セクション選択は保持する** (連続投入は同一セクション内が大半のため)
- **前タスクがマイルストーンの場合**: マイルストーンは終了日 = その日付なので、
  上記の規則がそのまま適用され、次のタスクはマイルストーン当日から開始する。
  特例は設けない (ゲート日にその日から次工程が立ち上がる、という実務上も自然な形)

### 項目 4: 日付入力

**課題として報告された内容**: 日程を手入力で打つしかない。カレンダー選択や
キーボードでの上下編集が欲しい。

**調査結果 ― 報告と実装が食い違っていた**: 日付欄は**すでに
`<input type="date">`** である (`src/app.js:251, 255, 463, 467`)。Chrome の
ネイティブカレンダーも、各セグメントでの ↑↓ キー編集も本来は機能する。

実測したところ、入力欄の背景は `rgb(33,38,45)` (ダーク) だが `color-scheme` は
`normal` (ライト扱い) のままだった。このため Chrome がカレンダーピッカーの
アイコンをライトテーマ用の黒いグリフで描画し、**暗い背景に溶けて不可視になって
いる**。機能が無いのではなく、アイコンが見えないだけである。

**設計**: `color-scheme: dark` を適用してネイティブ UI をダークテーマに合わせる。
キーボードでの ↑↓ 編集はネイティブ機能なので追加実装は不要。

**スコープ外として明示**: `after a1` 依存のタスクでは日付欄が空になるという別課題
が残っている。これは依存関係の表現方法の問題であり、本 spec では扱わない。

### 項目 5: マイルストーン

**課題**: milestone は `['none','done','active','crit','milestone']` の
ステータスボタンの 1 つでしかない (`src/app.js:429`)。選択しても開始日・終了日の
2 欄は残ったままで、Mermaid の構文 (日付 1 つ + 期間ゼロ) と食い違う。さらに
`addTask(text, sectionIndex, label, id, startDate, endDate)`
(`src/modules/gantt.js:242`) は **status 引数を持たない**ため、追加時点で
マイルストーンにすることが構造的に不可能で、「一度タスクとして作る → 選択 →
ステータス変更」しか経路がない。

**設計**:

- 追加フォームの先頭に **「タスク / マイルストーン」の種別トグル**を置く
- マイルストーンを選ぶと、開始日 + 終了日の 2 欄が **「日付」1 欄に畳まれる**
- 詳細パネル側も同じ規則で畳む (`status === 'milestone'` なら日付 1 欄)
- 生成される構文: `ラベル :milestone, id, 日付, 0d`
- `addTask` に status 引数を追加する (既存呼び出しは status 省略でタスク扱い)

```
種別  [ タスク | マイルストーン ]
ラベル [リリース判定          ]
ID    [                     ]
日付   [ 2026-05-13          ]   ← 1欄に畳む
セクション [ 設計           ▾ ]
[        + 追加             ]
```

## 実装順序と依存

| 順 | 作業 | 先行して完了している必要があるもの |
|---|---|---|
| 1 | 項目 4 (`color-scheme: dark`) | なし |
| 2 | 項目 1 (概観/詳細モード) | なし (renderProps 移行と独立) |
| 3 | **ADR-018 C 消化 (移行コミット、機能追加なし)** | なし |
| 4 | 項目 2 (セクション上下入替) | 移行コミット |
| 5 | 項目 5 (マイルストーン) | 移行コミット |
| 6 | 項目 3 (タスク連続入力) | 移行コミット、項目 5 |

項目 3 を項目 5 の後に置くのは、フォーカス対象と Enter 対象のフォームレイアウトが
項目 5 の種別トグル導入で変わるため。逆順にするとフォーカス管理を書き直すことになる。

項目 1 と 4 は renderProps 層に触れないため移行前に着手できる。

## テスト方針

**ベースライン**: `node tests/run-tests.js` = 379 passed / 0 failed (現時点)。

- **移行コミット**: ロジックは不変なので既存ユニットテストがそのまま回帰検出に
  使える。加えて **before/after のスクリーンショット一致**を合格条件とする
- **項目 2**: `moveSection` のユニットテスト (先頭/末尾での no-op、配下タスクの
  随伴、セクションが 1 つだけのケース)
- **項目 5**: `addTask` の status 付き呼び出し、`:milestone, id, 日付, 0d` の
  生成、詳細パネルでの畳み込み
- **項目 3**: 日程自動送りの計算 (期間維持、月跨ぎ、前タスクがマイルストーン)
- **項目 1 / 4**: GUI 描画そのものなのでユニットテストでは判定できない。
  **実機スクリーンショット検証を必須ゲート**とする (自動テストの GREEN だけでは
  visual regression を検出できない)

## リスクと対策

| リスク | 対策 |
|---|---|
| 移行が中途半端だと inline renderProps が外部側を shadowing し、古い UI が無言で表示され続ける | inline 定義の削除と外部側の追加を**同一コミット**で行う |
| `btn-zoom-fit` の再定義が他 20 図種へ波及する | `currentModule.type === 'gantt'` でガード。他図種は従来の `zoomToFit` を維持 |
| `useWidth` 変更でバーのドラッグ操作 (ADR-010) が壊れる | 座標系の一致は実測で確認済み (差 0)。残るは通し操作の確認のみ |
| モード切替後もそれ以前のズーム倍率が残り二重に縮小される | 切替時に `setZoom(1.0)` を必ず行う。**実測で踏んだ問題** |
| 詳細モードで横スクロールが出ない | 既存パイプラインが `width="100%"` をピクセル値へ正規化済み。追加実装は不要 |
| 移行の回帰と機能追加の回帰が混ざる | 移行を振る舞い不変の単独コミットに分離し、スクリーンショット一致で先に検証する |
