**日付**: 2026-08-18 (2026-08-19 全面改訂)

**関連**: MA ADR-018 (モジュールレジストリ merge)、横断 ADR-010 (日付⇔ピクセル変換)、横断 ADR-008 (SVGオーバーレイ)

## 改訂履歴

Critical 5 件・Major 8 件・Minor 6 件が判明したため全面改訂した。特に次の 2 件は

- 「`ctx.setMmdText` に同期 re-parse 修正がある」— 修正 (`a4e8410`) は

- 「テストベースライン 379 passed」— 本ブランチの実測は **365 passed**

いずれも PR #2 の作業ツリーで読んだ値を、master から分岐した本ブランチ向けの
仕様書に書いてしまったもの。**以後、数値と実装参照は必ず対象ブランチで取り直す。**

## 背景

実機で Gantt を操作した結果、5 件の課題が挙がった。いずれも Tier1〜Tier3 で
21 図種へ横展開を進める過程で、**Gantt だけが取り残された**ことに起因する。
Gantt は最初期に `src/app.js` へ inline 実装され、その後に整備された共通ヘルパ
(`window.MA.properties.*`)・ctx 契約・アクションバー規約のいずれにも乗っていない。

## 現状の実測値

計測環境: Chromium 1600x1000、**プレビューコンテナ幅 890px**、デフォルトの Gantt
サンプル (4 タスク / 2 セクション)。

| 項目 | 実測値 |
|---|---|
| mermaid が出力する SVG | `viewBox="0 0 1600 196"` / `width="1600"` |
| 適用される auto-fit ズーム | **54%** |
| タスク文字 | 11px → **実効 5.9px** |
| バー高さ / 幅 | 20px / 461px (2週間タスク) |
| `mermaid.initialize` の gantt 設定 | **なし** (`src/app.js:1050-1054`) |
| `node tests/run-tests.js` | **365 passed / 0 failed** |

`useWidth` を指定していないため mermaid 内部デフォルトの 1600 が適用され、内容が
4 タスクしかなくても SVG は常に横 1600px のキャンバスに引き伸ばされる。一方
フォントは 11px 固定。結果として「バーだけが横に肥大し、文字は固定サイズ」という
比率の不整合が生じる。

## 実機で確定した事実

すべて mermaid v11.13.0 (`lib/mermaid.min.js`) に対する実測。

### F1. `useWidth` は制御可能で、繰り返し有効

| useWidth | viewBox | SVG の `width` 属性 | バー幅 | フォント |
|---|---|---|---|---|
| 未指定 | `0 0 1600 196` | `1600` | 461px | 11px |
| 880 | `0 0 880 196` | `100%` | 232px | 11px |
| 2400 | `0 0 2400 196` | `100%` | 716px | 11px |

フォントは常に 11px、バー幅だけが `useWidth` に比例する。

### F2. `width="100%"` はパイプラインが正規化する

既存の描画パイプライン (`src/app.js:840-849`) が毎回
`svgEl.removeAttribute('style')` でインラインスタイルを捨て、viewBox 幅をピクセル値
として `width` / `height` に設定し直し、overlay も同じ viewBox に同期する。

**`width="100%"` のまま `#preview-svg` (display:inline-block) に置くと表示幅が
161.98px に潰れる。** 上記の正規化はその対策そのものであり、両モードとも
ピクセル値で確定させる必要がある。

### F3. 座標系は揃う ― ADR-010 は座標変換の面では壊れない

`useWidth = 436` (当時のコンテナ幅。上表の 890px とは別条件) で計測:

| 項目 | 実測 |
|---|---|
| SVG の `width` 属性 | `436` (`100%` ではない) |
| preview と overlay の viewBox | 完全一致 |
| 較正 `getBBox()` と ドラッグ `getScreenCTM().inverse()` の X 差 | **0** |

`setZoom(1.0)` 後に画面上で +5 日ぶんドラッグ → `2026-04-01` → `2026-04-06` と正確。
ドラッグは CSS transform も viewBox スケールも吸収する。

**ただしこれは「較正の入力が正しい」場合に限る (F5 参照)。**

### F4. モード切替時は `setZoom(1.0)` が必須

`useWidth` を変えただけでは**それ以前のズーム倍率が残り、CSS transform で二重に
縮小される**。実測ではコンテナ幅に合わせたのにズーム表示が 44% のままだった。
auto-fit は初回描画時 (`thisRender === 1`) にしか走らない。

### F5. マイルストーンは較正を壊す

マイルストーンの描画実体は `rect.task.milestone` 20×20 + CSS `rotate(45deg)`。
`getBBox()` は回転前の外接矩形を返すため、**日付位置ではない x** が較正に入る。

| | pxPerDay | 実装タスクの逆算日付 (正解 2026-04-16) |
|---|---|---|
| マイルストーン無し | 19.267 | 2026-04-16 |
| マイルストーン有り | 18.571 | **2026-04-17** |

**マイルストーンを 1 個置くだけで、無関係なタスクのドラッグ結果がずれる。**
誤差は原点から離れるほど拡大する。

### F6. `mermaid.initialize` はマージではなく置換

| 操作 | viewBox | バー色 |
|---|---|---|
| アプリ既定 (`theme: dark`) | 997 | `rgb(89,92,92)` |
| `{gantt:{useWidth:880}}` のみ渡す | 880 | **`rgb(138,144,221)`** (テーマが飛ぶ) |
| `{startOnLoad,theme,securityLevel}` のみ渡す | **997** (useWidth 消滅) | `rgb(89,92,92)` |

部分的に渡すと `theme` dark→default、`securityLevel` loose→strict、
`startOnLoad` false→true になる。

### F7. マイルストーン構文

| 記法 | 結果 |
|---|---|
| `ラベル :milestone, m1, 2026-05-13, 0d` | 正常描画 |
| `, 1d` | 描画されるが位置が 1 日ずれる |
| `:milestone, m3, 2026-05-13` (期間省略) | **Error: Invalid date:m3** (id が日付と解釈される) |
| `:milestone, m4, after a1, 0d` | 描画可。parse は `startDate=null / after='a1' / endDate='0d'` |
| `:milestone, 2026-05-13, 0d` (id 省略) | 描画可。パーサ側は `__auto_0` を採番 |

**`0d` は省略不可。**

### F8. 幅を広げるほど日付軸は疎になる

mermaid の目盛本数は幅にほぼ依存せず 10〜12 本で一定。

| 期間 | useWidth | 目盛本数 | 間隔 | ラベル |
|---|---|---|---|---|
| 1 年 | 8,766 | 12 | 約 700px | 判別可 |
| 10 年 | 87,660 | 10 | 8,749px | **全部 `01/01`** (年が出ず区別不能) |

描画コスト自体は問題ない (10 年 60 タスクで render 19ms / layout 2ms /
calibrate 1ms / SVG 8.4KB)。**問題はサイズではなく軸ラベルの疎化。**

### F9. 日付演算の破綻ケース

| 式 | 結果 |
|---|---|
| `daysBetween('2026-04-01','5d')` | **NaN** |
| `addDays(x, NaN)` | **例外 `Invalid time value`** |
| `daysBetween(null,'2026-04-01')` | 20544 (null が 1970 起点) |
| `addDays(null, 5)` | **`1970-01-06`** |
| `2028-02-28 + 1d` | `2028-02-29` (正しい) |
| `2026-12-25 + 20d` | `2027-01-14` (正しい) |

月跨ぎ・年跨ぎ・うるう日は正しい。壊れるのは duration 形式と after 形式。
**デフォルトサンプルの 2 件目が `after a1` なので初期状態から踏む。**

## 設計方針: 移行を先行する (再判断済み)

初版の主要根拠 (`a4e8410` の同期 re-parse 修正) は本ブランチでは成立しないため
撤回した。訂正した前提でレビュアーに再判断を依頼した結果、**結論は変わらず
「移行を先行する」**。ただしスコープと手順は下記のとおり大きく縮小・分割された。

### 根拠

1. **5 項目のうち 3 つ (2/3/5) が移行対象コードそのもの** — 不変
2. ADR-018 の据え置き根拠 (「app.js の内部関数と密結合」) が事実誤認。実際は逆で、
   `calibrateScale` を含む 24 個の関数を `src/modules/gantt.js` から import している
3. **項目 3 は stale-parse 対策をどの案でも必要とする。** `a4e8410` が直したのと同じ
   操作形状であり、master の ctx にも inline にも修正が無い以上、必ずどこかに入る。
   移行すれば置き場所は `ctx.setMmdText` の **1 箇所**で全 21 図種が恩恵を受ける。
   移行しなければ inline gantt 専用に実装し、後日の移行で捨てるコードになる

### 移行スコープ (再測定で縮小)

| メンバ | 箇所 | 扱い |
|---|---|---|
| `updateText` | `app.js:741` | **死にコード。削除するだけ** |
| `exportMmd` | `app.js:748` | **死にコード。削除するだけ** |
| `type` / `detect` / `parse` / `template` | — | 外部 `gantt.js` に既にある |
| `buildOverlay` | `app.js:99` | 移行対象。3 引数化 |
| `renderProps` | `app.js:191` | 移行対象。ctx 4 引数化 |

`updateText` / `exportMmd` に呼び出し元が無いことは実測で確認済み
(`grep -rn "exportMmd\|\.updateText(" src/ mermaid-assist.html tests/` が定義行
以外 0 件)。

ドラッグ処理 (`app.js:1240-1420`)・`getCalibration`・`dragState` は **inline
`modules.gantt` オブジェクトのメンバではない。** ADR-018 C の対象は「inline
モジュールオブジェクトの廃止」なので、ドラッグ層は app 側のオーバーレイ操作層として
残してよい (`gantt.js` の純関数を alias 経由で使い続ける現行構造のまま)。

**実質の移行対象は `renderProps` と `buildOverlay` の 2 メンバ。**

### 移行の原子性: 「1 コミット全移行」を撤回

初版は「inline 削除と外部追加を同一コミットで」= 一括 1 コミットとしていたが、
shadowing の本当の不変条件は**メンバ単位**である。ADR-018 の merge は
`for (var _prop in _mod) { if (!(_prop in modules[_key])) ... }`
(`app.js:81-85`) と**プロパティ単位**で欠落分だけ補完する。実測で確認済み。

したがって危険なのは「inline にメンバが残ったまま外部に同名を足す」ことであり、
**「inline から該当メンバを削除」と「外部に同メンバを追加」を同一コミットで行う
限り、メンバごとの段階移行は安全**。

一括 1 コミットは差分が大きすぎてレビュー不能で、失敗時の切り戻しも粗い。
段階方式なら、スクリーンショットで捉えられないもの (当たり判定・選択 ID 解決・
ドラッグ後の日付) を各段階の**操作ベース E2E** で個別に固定できる。

### 移行手順 (各コミットが独立に検証可能)

| # | 内容 | 検証 |
|---|---|---|
| 1 | **死にコード削除** — `updateText` / `exportMmd` | 挙動不変。grep 証明をコミットメッセージに残す |
| 2 | **`buildOverlay` 移行** — 3 引数化し、特例 3 箇所のうち `rebuildOverlay` (`app.js:39-43`) と `refresh()` 内 (`872-877`) の 2 箇所を削除 | オーバーレイのクリック選択・バードラッグ→**日付アサーション**・スクショ |
| 3 | **`renderProps` 移行** — ctx 4 引数化し、ディスパッチャ特例 (`918-921`) を削除 | パネル操作 E2E + スクショ。**前提: stale-parse 修正が ctx に存在すること** |
| 4 | **残骸削除** — inline オブジェクトと inline 登録コードを削除し、`modules.gantt` が外部モジュールそのものになる | 全 E2E + スクショ |

### 前提作業: stale-parse 修正の取り込み (**未決定・要判断**)

手順 3 の前提として、`ctx.setMmdText` に同期 re-parse 修正が入っている必要がある。
取り込み方に 2 案あり、**Kawano さんの判断待ち**:

- **案 A (推奨)**: **PR #2 を先に master へマージし、gantt ブランチを切り直す**
  - `a4e8410` が検証済みの形で自然に入る (単独 cherry-pick の再検証が不要)
  - PR #2 には `actionBarHtml` / `bindActionBar` ヘルパと 6 モジュールのパネル改修が
    入っている。**gantt 移行後のパネルは当然この新規約で書くべき**で、master 直分岐で
    移行すると PR #2 マージ後に gantt パネルをもう一度触ることになる
  - gantt 移行は app.js の大規模削除であり、PR #2 の app.js 変更と並走すると
    コンフリクト解消コストが高い。直列化が安い
- **案 B (次善)**: `a4e8410` を gantt ブランチの**先頭に単独 cherry-pick** し、その
  コミットだけで検証を完結させる (全ユニット + sequence の並び替え E2E + 実機確認)。
  挙動が実際に変わる変更なので機能追加と混ぜない

### 「振る舞い不変」の合格条件 (初版から強化)

スクリーンショット一致だけでは不十分。**捉えられないもの**: オーバーレイの当たり
判定、選択 ID の解決結果、ドラッグ後の日付、フォーカス位置。

合格条件を次に置き換える:

1. スクリーンショット一致
2. 既存 e2e (`tests/e2e/gantt-basic.spec.js`、`after-dependency-drag.spec.js`) GREEN
3. **ドラッグ結果の DSL テキスト一致**

移行前に現行ブランチで e2e のベースラインを保存しておくこと。
なお `exportMmd` は死にコードなので検証対象から外れる。

## 機能設計

### 項目 1: 概観モード / 詳細モード

**課題**: 現行の auto-fit は CSS `transform: scale()` で **文字ごと縮めている**
(`src/app.js:862-869`)。全体を収めると文字が読めない。

**設計**: 2 モードを導入し、`useWidth` で描画そのものを制御する。
**両モードとも SVG の `width` はピクセル値で確定させる** (F2)。両モードの差は
`useWidth` の値だけ。

| モード | `useWidth` | ズーム | 結果 |
|---|---|---|---|
| 概観 | `コンテナ clientWidth − 32 − スクロールバー幅` | 100% | 全期間が横に収まり、文字は 11px を維持 |
| 詳細 | `max(概観幅, 日数 × DETAIL_PX_PER_DAY)` | 100% | 横スクロールで全期間を辿る |

**スクロールバー幅を引く理由**: 40 タスクの実測で、縦スクロールバー出現により
`clientWidth` が 890→884 に減り、6px の横スクロールバーが出た。概観の不変条件
「横に収まる」が縦長の図で常に破れる。`#preview-container` を
`overflow-y: scroll` 固定にする案でもよい。

**日付軸の粒度 (F8 への対応)**: `useWidth` だけを変えると軸ラベルが疎になり、
長期案件では判別不能になる。`useWidth` と同時に `gantt.tickInterval` と
`axisFormat` を期間に応じて決める:

| 期間 | tickInterval | axisFormat |
|---|---|---|
| 3 ヶ月以下 | `1week` | `%m/%d` |
| 2 年以下 | `1month` | `%Y/%m` |
| それ以上 | `3month` | `%Y/%m` |

**`DETAIL_PX_PER_DAY` は初期値 24px/日**とする。この値は理論的に導けないため実機
検証で調整し、結果を実装計画に記録する。

**縦方向**: 横だけ収め、縦はスクロール。バー高さ (20px) とフォント (11px) は常に固定。

**概観モードでの細いバーの扱い (初版の判断を撤回)**: 初版は「最小バー幅を設けない。
対価は細部が見えないこと」と書いたが、**実際の対価は誤操作だった。**

3 年スパン (1.31px/日) の実測でバー幅が `[19, 0, 2, 19]` になり、`calibrateScale` の
候補フィルタ (`width >= 3`、`gantt.js:483-486`) で 1 日タスクと 3 日タスクが脱落。
さらに y 近傍マッチ (`< 30px`、行間 24px) の結果、3 件目のタスクに 4 件目の rect が
割り当てられた。**細いタスクをクリックすると別タスクが選択され、ドラッグすると別
タスクの日付が書き換わる。** 無反応より悪い。

対応 (いずれか、実装時に決定):

- **推奨**: 較正の行マッチを y 近傍から**行インデックス**に変える (述語を 1 つに統一)
- 代替: マッチ不能タスクがある場合は概観でオーバーレイ操作を無効化し、ステータスバー
  に理由を表示する

**切替 UI**: 新規 UI を追加せず、既存の `btn-zoom-fit` を再定義する。

```
通常時:  [−] [ 100% ] [+] [ fit ]      ← fit 押下で概観モードへ
概観中:  [−] [ 概観 ] [+] [ fit ]      ← ± を押すと詳細モードへ復帰
```

**他図種への波及防止**: `btn-zoom-fit` は全図種で共有されている。再定義は
`currentModule.type === 'gantt'` でガードする。

**`useWidth` の注入方法 (F6 への対応)**: `mermaid.initialize` は置換セマンティクス
なので、部分的に渡してはならない。**全設定を組み立てて渡す単一関数
`applyMermaidConfig({ ganttUseWidth, tickInterval, axisFormat })` を作り、
`mermaid.initialize` の呼び出しをその 1 箇所に限定する。**

モード状態は**アプリ側の変数を真とし、mermaid の config はその派生物**とする。
config にしかモード状態が無いと、将来 `initialize` を呼ぶコードが 1 箇所増えるだけで
モードが無言で失われる。

**再計算契機 (M4 への対応)**: 詳細モードの `useWidth` はテキスト編集のたびに変わる。
「モード切替ごとの initialize」では足りない。**描画パイプラインの先頭で常に config を
再構成する**ことを `refresh()` の責務として設計に含める。

**ADR-010 との関係**: 座標系は揃う (F3)。ただし**マイルストーンが混在すると較正の
入力自体が壊れる** (F5)。項目 5 の必須要件として対処する (下記)。

### 状態機械の定義

初版で未定義だった遷移をすべて定義する。状態は `mode ∈ {概観, 詳細}` と `zoom`。

| # | 事象 | 動作 |
|---|---|---|
| 1 | ウィンドウリサイズ | 概観中は `useWidth` 再計算 + 再描画。現状 resize リスナが 0 件なので追加が必要 |
| 2 | ペインリサイズ (`app.js:1528-1535`) | 同上。現状は `scheduleRefresh()` のみで `useWidth` 据え置き |
| 3 | 概観中のテキスト編集で期間が伸縮 | `useWidth` は概観幅のまま (期間に依存しない)。軸粒度は再判定 |
| 4 | 詳細中のテキスト編集 | `useWidth = 日数 × px/日` を毎描画で再計算 |
| 5 | 概観中に再度 fit | no-op |
| 6 | ズーム 100% 以外で fit | 概観へ入り `setZoom(1.0)` を強制 |
| 7 | 概観中に zoom-in/out | 詳細へ復帰し、`zoom` は押下前倍率ではなく **100% + 1 段** から始める |
| 8 | undo/redo (`app.js:1060-1069`) | テキスト復元後に config 再構成を通す (再計算契機に含める) |
| 9 | 概観中の図種切替 (`app.js:1549-1557`) | モード変数を詳細へリセットし、config の `useWidth` も破棄 |
| 10 | 図種を gantt に戻す | 詳細モードで開始 |
| 11 | 概観中のドラッグ | **禁止しない。ただし px/日 がドラッグ中に変化する** (F10 参照)。実装時に再評価 |
| 12 | 起動直後 | 詳細モード + 従来の auto-fit CSS スケール (既存挙動を維持) |
| 13 | ファイル読込 / テンプレート読込直後 | 詳細モード |
| 14 | パースエラーから復帰 | 直前のモードを再適用 |
| 15 | タスク 0 件 / 日付付きタスク 0 件 | 日数が定義できないため詳細も概観幅を使う |

**F10 (未解決の懸念)**: 概観モードは固定幅キャンバスなので、編集のたびに px/日 が
変わる。実測でドラッグ 1 回で 16.11→18.14 px/日 と変化した。ドラッグ中は 100ms 毎に
再描画される (`DRAG_RENDER_INTERVAL`) ため、掴んだバーの下でスケールが動く。
実装時に実機で操作感を確認し、必要なら概観中のドラッグを禁止する。

### 項目 2: セクションの上下入れ替え

**課題**: セクション一覧の各行 (`src/app.js:224-229`) には `✕` 削除ボタンしかない。
タスク側には `prop-move-up` / `prop-move-down` がある。

**設計**: セクション一覧の各行に ↑ ↓ を追加する。移動は配下タスクを伴う。
`src/modules/gantt.js` に `moveSection(text, sectionIndex, direction)` を追加。

**ブロック範囲の定義 (初版は未定義だった)**:

- 先頭 = `section` 行
- 末尾 = 次の `section` 行の直前
- **直前の空行は含めない**
- 入れ替え後に空行を正規化する

既存の `deleteSection` (`gantt.js:341-360`) は直前の空行も巻き込む非対称実装なので、
同じブロック定義を使うと空行がドリフトする。`moveSection` は上記定義を採り、
差異を実装計画に記録する。

**暗黙開始日タスクの扱い (M7 への対応)**: mermaid では開始日を省いたタスク
(`A :a1, 5d`) は直前タスクの終了後に始まる。**セクションを入れ替えると、暗黙開始日
タスクの実際の日付が変わる。** テキストブロックの入れ替えは日付の観点で不変ではない。

対応: 移動対象ブロックまたは移動先の隣接位置に暗黙開始日タスクが含まれる場合、
**移動前に日付を明示化してから移動する**。これにより見た目の日付が保存される。

`sanitizeAfterDependencies` (`gantt.js:296-328`) との相互作用も実装時に確認する。

### 項目 3: タスクの連続入力

**課題**: `propsEl.innerHTML = ...` によるパネル全面再構築でフォーカスが消失する。
Enter キーでの追加バインドもない。

**設計**:

- 追加フォームのいずれのフィールドでも **Enter で追加を実行**
- 追加後、**ラベル欄へフォーカスを戻し、テキストを全選択**
- **日程を自動送り**: 次の開始日 = 前タスクの終了日。期間 (日数) は維持
- **セクション選択は保持**

**「前タスク」の定義 (初版は未定義だった)**:

> 選択中セクション内の最終タスクで、`startDate` と `endDate` が**両方とも
> `DATE_RE` を満たすもの**

満たさない場合のフォールバック:

| 状況 | 動作 |
|---|---|
| 前タスクが無い (1 件目 / 空セクション) | 自動送りせず、**日付欄は空のままフォーカスだけ返す** |
| 終了日が duration (`5d`) | 同上 |
| 開始日が `after` | 同上 |

実終了日は parse の解決値を使い、**解決不能なら自動送りを諦めて日付欄を空にする**。
前回値を残す案は、ユーザーが気づかなければ静かに誤った日付が入る。例外死と 1970 年
混入の両方を潰したうえで、**静かな誤データより明示的な無入力を選ぶ**。

日付欄が空のまま追加ボタンを押した場合の扱い (拒否するか、日付なしで追加するか) は
実装時に決め、実装計画に記録する。

**F9 のとおり、これらを素通しすると例外死または 1970 年の日付が入る。**
受入条件に「4 形式 (日付・duration・after・空) すべてで例外を出さない」を含める。

**フォーム状態の保持 (M8 への対応)**: `renderProps` はエディタの 1 キーストロークごと・
選択変更ごとにも走り、追加フォームの日付はハードコード
(`value="2026-04-01"` / `"2026-04-15"`、`app.js:251,255`) なので、**手入力した日付が
次の refresh で消える。** 自動送りの既定値とユーザーが直した「並行工程の日付」が
毎 refresh で競合し、「並行工程のときだけ日付を直す」ワークフローが成立しない。

**追加フォームの入力値 (ラベル / ID / 日付 / セクション / 種別) は再描画をまたいで
保持する。** クリア契機は「追加成功時」と「図種切替時」のみとする。

**ID 採番 (m5 への対応)**: 現行の `'t' + (++addCounter)` (`app.js:299`) は既存 ID と
衝突しうる。連続入力で確率が上がり、衝突すると `after` 参照先が変わる。
**既存 ID 集合を見て衝突しない採番にする。**

### 項目 4: 日付入力

**課題として報告された内容**: 日程を手入力で打つしかない。

**調査結果 ― 報告と実装が食い違っていた**: 日付欄は**すでに `<input type="date">`**
(`src/app.js:251, 255, 463, 467`)。実測で `color-scheme` が `normal` のまま、入力欄の
背景が `rgb(33,38,45)` (ダーク) だったため、Chrome がカレンダーアイコンをライト
テーマ用の黒いグリフで描画し、暗い背景に溶けて不可視になっていた。

**設計**: `color-scheme: dark` を適用する。キーボードでの ↑↓ 編集はネイティブ機能
なので追加実装は不要。

**セレクタの確定 (m2 への対応)**: `:root` に当てるとスクロールバーや `select` など
**21 図種すべてのネイティブ UI が変わる。** 適用範囲を日付入力に限定するか、全体に
当てるかを実装時に決め、いずれの場合も実機スクリーンショット検証の対象に含める。

### 項目 5: マイルストーン

**課題**: milestone はステータスボタンの 1 つでしかなく (`app.js:429`)、選択しても
開始日・終了日の 2 欄が残る。`addTask(text, sectionIndex, label, id, startDate,
endDate)` (`gantt.js:242`) は status 引数を持たないため、追加時点でマイルストーンに
できない。

**設計**:

- 追加フォームの先頭に **「タスク / マイルストーン」の種別トグル**
- マイルストーン選択時は日付 2 欄を **「日付」1 欄に畳む**
- 詳細パネルも `status === 'milestone'` なら同様に畳む
- 生成構文: `ラベル :milestone, id, 日付, 0d` (**`0d` は省略不可**、F7)
- `addTask` に status 引数を追加する

**較正への影響 (F5 / C3 — 初版に記載が無かった必須要件)**:

マイルストーンの `rect` は 20×20 + CSS `rotate(45deg)` で、`getBBox()` が日付位置を
返さない。**マイルストーンを 1 個置くだけで無関係なタスクのドラッグ結果がずれる。**

**必須対応**: `calibrateScale` の候補 rect から `status === 'milestone'` のものを
**除外する** (または中心 x へ補正する)。ユニットテストに
**「マイルストーン混在で pxPerDay が変わらない」**を必ず含める。

**この較正修正は項目 5 の UI より先に入れる。** `gantt.js` の純関数なので移行とも
独立にユニットテストでき、先に入れておけば項目 5 の実装時に較正の正しさを前提に
できる。

これを落とすと、項目 5 を入れた瞬間に横断 ADR-010 の前提が崩れる。

**種別トグルと status の整合 (述語の非対称への対応)**: 「マイルストーンか否か」を
判定する経路が、既存の status キーワード判定と新設の種別トグルの 2 つになる。
**status を唯一の真とし、トグルは status への入力手段に過ぎない**と定義する。
詳細パネルで status を milestone にしたら日付欄は即座に 1 欄へ畳む。

## テスト方針

**ベースライン**: `node tests/run-tests.js` = **365 passed / 0 failed** (本ブランチ実測)。

### mermaid.render を通すゲート (最重要)

**`mermaid.parse` を通っても `mermaid.render` で落ちるケースがある。** 自作パーサ
(`parseGantt`) のユニットテストだけでは、mermaid が受理するかを見ていない。

実例: `:milestone, m3, 2026-05-13` (`0d` 無し) は `parseGantt` が
`status=milestone / startDate=2026-05-13` と問題なく解釈するが、`mermaid.render` は
`Error: Invalid date` で落ちる。

**項目 2 / 5 の受入条件に「生成テキストが `mermaid.render` に通り、かつ意図した
日付で描画される」を含める。**

### 項目別

| 項目 | テスト |
|---|---|
| 1 | 実機スクリーンショット。モード切替 → **ドラッグ → 日付が正しい**の通し操作。**両モードでのエクスポート**(下記) |
| 2 | `moveSection` の単体 (先頭/末尾で no-op、配下タスクの随伴、暗黙開始日タスクの日付保存、空行の正規化) + render ゲート |
| 3 | 日程自動送り (期間維持、月跨ぎ、4 形式で例外を出さない)、フォーム状態の保持、ID 衝突 |
| 4 | 実機スクリーンショット (アイコンが実際に見えること) |
| 5 | `addTask` の status 付き呼び出し、`0d` 付き構文の生成、**マイルストーン混在で pxPerDay が変わらない**、render ゲート |

### エクスポートの検証 (未検証の懸念)

`exportPNG` は `svgToCanvas` で `img.width` を canvas サイズに使う (`app.js:1080` 付近)。

- 概観で `width="100%"` を残す設計だとここが 0 または誤サイズになる → F2 の
  ピクセル確定で回避できるはずだが未実験
- 詳細モードの 87,660px 出力は **Chrome の canvas 上限 (約 65,535px) を超える可能性**

**項目 1 の受入条件に「両モードでエクスポートが正しい」を含める。**

## リスクと対策

| リスク | 対策 |
|---|---|
| `mermaid.initialize` の置換で theme / securityLevel が飛ぶ | `applyMermaidConfig()` 1 箇所に集約し常に全設定を渡す。モード状態はアプリ変数が真 |
| マイルストーンで較正が壊れ、無関係なタスクのドラッグがずれる | 較正候補から milestone rect を除外。ユニットテストで固定 |
| 概観で細いバーが誤選択・誤編集される | 較正の行マッチを行インデックスに統一。または概観でオーバーレイ操作を無効化 |
| 日程自動送りが例外死する | 「前タスク」の定義とフォールバックを明示。4 形式で受入テスト |
| 詳細モードで軸ラベルが疎化し判別不能になる | `tickInterval` / `axisFormat` を期間に応じて決める |
| 概観幅がスクロールバー分だけ超過する | `clientWidth − 32 − スクロールバー幅`、または `overflow-y: scroll` 固定 |
| 移行の回帰がスクショで捉えられない | e2e GREEN + ドラッグ結果の DSL 一致を合格条件に加える |
| 移行が中途半端だと shadowing で古い UI が出続ける | inline 削除と外部追加を同一コミットで |
| `btn-zoom-fit` の再定義が他 20 図種へ波及する | `currentModule.type === 'gantt'` でガード |

## スコープ外

- `after a1` 依存タスクで日付欄が空になる件
- Gantt 以外の 20 図種への概観/詳細モードの展開
- `displayMode: 'compact'` の採用
- `package.json` の version が 1.0.0 のまま tag と乖離している件
- `dateUtils.addDays` (`src/core/date-utils.js:8-12`) がローカル時刻 `setDate` +
  `toISOString` のため DST 帯で 1 日ずれ得る件 (JST では顕在化しない。項目 3 が
  強く依存するので前提として記録のみ)
- gantt の図種判定が 2 種類の述語で行われている件
  (`modules.gantt.detect` は `text.trim().startsWith('gantt')`、他図種は
  `parserUtils.detectDiagramType` の firstNonEmpty 行判定)。先頭に `%%{init}%%`
  ディレクティブやコメント行がある gantt を mermaid は受理するのに detect が外す
  可能性がある。**移行で detect も外部へ寄せるため、移行時に確認すること**
