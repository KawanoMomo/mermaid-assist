# 批判レビューの記録

`docs/quality-gate.md` の合格判定に使った、実際に回したレビューの記録。
**何を、どの観点から、どう測って、何が出たか**を残す。出なかったことも残す —
「調べていない」と「調べたが出なかった」は違う。

## 方式

サブエージェントによる並行レビューを試みたが、この環境では起動したエージェントが
完了報告を返さなかった (最初の3体、絞り込み後の3体、診断用の最小タスク1体、
いずれも無応答)。**待ち続けても閉じないループより、閉じるループを選んだ。**

代わりに、観点ごとに独立した検証スクリプトを書き、**実プロセスとして同時に走らせた**。
各観点は別のブラウザインスタンスで動き、結果をファイルに残す。

## 観点A: アクセシビリティ / キーボード完結性

| 項目 | 結果 |
|---|---|
| 名前の無いボタン | なし (全ボタンにテキストか title) |
| Tab 到達可能な要素 | 35 |
| オーバーレイの tabindex | 0件。ただし矢印キーによる巡回を実装済みで、キーボードだけで全要素に到達できる |
| `<html lang>` | `ja` |
| ステータスバー | `rgb(139,148,158)` / 背景 `rgb(22,27,34)` / 11px |

**指摘なし。**

## 観点B: データ整合性 (同じ値で書き戻して内容が変わらないか)

21図種すべてでテンプレートをパースし、各要素のラベルを**同じ値で**書き戻して、
要素集合が変わらないことを確認。

- 20図種: OK (書き換え0件、要素集合が同一)
- kanban: 一度「★ 要素が変わった」と出たが、**検証スクリプト側の誤り**だった。
  `updateColumn(text, line, newName)` は第3引数が値なのに、スクリプトが汎用の
  `(text, line, field, value)` を仮定して `'label'` を渡していた。
  実機で列名を `Todo` → `作業待ち` に変えて意図どおり動くことを確認済み。

**実装の指摘なし。** ただし更新関数のシグネチャがモジュール間で揃っていない
(`updateColumn(text,line,value)` と `updateTaskField(text,line,field,value)`) のは
事実で、呼び出し側が間違えやすい。今回は誤検出だったが、将来の呼び出しミスの
温床にはなる。

## 観点C: 壊れた入力への堅牢性

8種の入力で pageerror が出ないことを確認。

| 入力 | status | pageerror |
|---|---|---|
| 空文字 | Error | なし |
| 空白だけ | Error | なし |
| 未知の図種 | Error | なし |
| 途中で切れた記法 | Error | なし |
| 5000文字の1ラベル | OK | なし |
| 制御文字 (NUL/BEL) | OK | なし |
| HTMLタグ入りラベル | Error | なし |
| 40段ネストの block | Error | なし |

**指摘なし。** status=Error は mermaid が拒否した表示であって、アプリは生きている。
どのケースでもプロパティパネルは描画され、エディタは操作可能なまま。

## 観点D: 性能回帰

| ノード数 | 流し込み→描画 | 1打鍵→反映 | overlay | 選択1回 | 矢印1回 |
|---|---|---|---|---|---|
| 20 | 56ms | 45ms | 21 | 83ms | 60ms |
| 60 | 90ms | 102ms | 61 | 83ms | 55ms |
| 120 | 159ms | 227ms | 121 | 68ms | 56ms |

**指摘なし。** 今回追加した処理 (オーバーレイの座標変換、選択の生存確認、
キーボード巡回) は要素数に対して線形で、120ノードでも体感を損なわない。

## 観点E: 自作コードへの敵対検証 (接続モード)

新しく書いたコードほど検証が薄いので、直前に実装した接続モードを標的に
3周のループを回した。詳細はコミット
`fix(connect): 自作の接続モードを自分で敵対検証して見つけた5件` に記録。

| 周 | 検出 |
|---|---|
| 1 | 図種切替でモードが残り別図に誤接続 / Escape で抜けられない / モード表示が無い |
| 2 | モード中に矢印キーで選択が動く / 始点を消しても線が引ける |
| 3 | 新規なし (収束) |

## 総括

実装に対する指摘は観点Eからのみ出た。A/C/D は問題なし、B は検証スクリプト側の
誤りだった。**「出なかった」を根拠にするために、何をどう測ったかを上に残している。**

### 訂正 (2026-08-21)

上の「規約は元から無い」は**不正確**だった。ADR-022 (採択済み) が
アクションバーのボタンに `sel-<kind>-<action>` という規約を定めている。
ただしその適用範囲は `actionBarHtml` が生成するボタンに限られており、
同 ADR は「プレフィックスの `<kind>` 部分は**モジュール内で一意**であれば良い
(モジュール間は独立)」と明記している。

つまり正しくは「**範囲を限定した規約は存在し、モジュール間の独立は意図的な決定**」。
私は ADR を見ずに「規約が無い」と断定し、実装前の ADR 確認ゲートを飛ばしていた。
実行すべきは「規約が実在するかを推測で判断する」ことではなく、**ADR を先に読む**ことだった。

なお `sel-node-connect` と `block-edit-connect` の不揃いは `connectButtonHtml` 由来で
ADR-022 の範囲外。規約違反ではないが、規約の趣旨からは外れている。

# 第4ラウンド: 実務の名前を入れる (2026-08-21)

日本語の設計書で使う名前は素直な英数字ではない。「設計(詳細)」「配列[0]」「A#1」
「"引用"付き」— これらは mermaid の DSL では意味を持つ記号なので、そのまま本文に
置くと図が壊れるか、**入れた文字が黙って消える**。r11-specialchars で21図種に
10種類の実名を流し込み、実描画まで見た。

## 見つかった欠陥

| # | 重大度 | 内容 | 実描画での症状 |
|---|---|---|---|
| A27 | Major | mindmap: 形状記号を含むラベル | 「設計(詳細)」→ 図には**「詳細」だけ**。( が形状指定として食われ前半が捨てられる。エラーは出ない |
| A28 | Major | block: 引用符を含むラベル | parse 失敗で図が出ない |
| A29 | Minor | sequence: # を含むラベル | 「A#1」→「A」。# 以降が実体参照として食われる |
| A30 | Minor | エラー表示が読めない | 一文がペインの右端で切れる。コンテナに scale(zoom) がかかっており、文字も拡大率のまま出るため |

A27〜A29 は引用囲み / `#quot;` / `#35;` に逃がして解決した。読み戻しで実体を戻すので
往復する。記号を含まないラベルは囲まないので、差分は増えない。

## 直せないもの (mermaid 側の制限)

| 図種 | 制限 | 実測 |
|---|---|---|
| architecture-beta | ラベルは `[A-Za-z0-9_ ]` のみ | 日本語・ハイフン・括弧すべて不可。引用囲みも効かない |
| sequence | participant 別名に `;` 不可 | 生でも引用囲みでも parse 失敗 |

こちらでは直せない。ただし出るエラーは `Lexer error on line 3, column 25` で、
利用者は自分の入力のどの文字が悪いのか分からない。**直せないものを黙って壊れさせ
ない**ため、原因を日本語で名指しする診断 (`src/core/diagnose.js`) を足した。
推測はせず、規則に当てはまる入力が本文に実在するときだけ言う。

これに合わせて r11 の判定基準も変えた。問うのは「通るか」ではなく
**「原因を名指しできているか」**。診断を空にする変異を入れると11件を検出する。

## 単体テストが通っても意味が無かった例

SC-1〜SC-3 (mindmap の括弧・角括弧・波括弧) は、修正前から**通っていた**。
パーサが `[...]` の中身をそのまま返すので、モジュール単位では往復して見える。
図に出ないことは実描画でしか分からない。パーサと mermaid で「往復した」の述語が
違う、という同じアーキタイプ。

| レビュアー | 壊した所 | 検出 | 復元後 |
|---|---|---|---|
| r11 | 診断が何も言わない | 11件 | 0件 |

# 第8ラウンド: 観点15 と、残りの UI 指摘 (2026-08-21)

## 新観点 r15-state-carryover

「文書が入れ替わったのに、前の文書の状態が残っていないか」。

図種を切り替えると本文はひな形に置き換わる。そのとき **残ってよい状態**(ズーム、
Undo 履歴 — 切替そのものを取り消せる)と **残ってはいけない状態**(前の文書に紐づく
入力値、選択、絞り込み)がある。

| 見たもの | 結果 |
|---|---|
| 一覧の絞り込み | 行数が閾値未満になると欄ごと消えるので、古い絞り込みが残らない |
| **追加フォームの入力** | **gantt だけ残った** — 本文はひな形に置き換わっているのに、名前と日付が前の図のまま |
| Undo 履歴 | 図種切替を取り消せる(設計どおり) |
| 選択 | 切替で消える |

gantt だけ該当したのは、他の図種がフォームを毎回作り直すのに対し、gantt は追加フォームの
状態をモジュール側で保持しているため。M2 の移設で addForm を gantt.js に移したことで、
**同じ問題がモジュールの寿命に紐づくようになった**とも言える。

対処はモジュール契約に `resetTransientState()` を足し、文書が入れ替わる2箇所
(図種切替 / ファイルを開く)で呼ぶ形にした。実装していないモジュールは何もしなくてよい。

## 調べて「欠陥ではない」と分かったもの

「図種を切り替えて gantt に戻すとオーバーレイのバーが1本しか出ない」を追った結果、
**本文自体が1タスク**だった。`gantt.template()` は1タスクで、起動時のサンプル(4タスク)
とは別物。切替時は template() が読み込まれるので、バー1本は正しい。

M2 の移設前後で同じ測定をしていたので回帰でないことは分かっていたが、原因まで特定した。
**「起動時のサンプル ≠ モジュールのひな形」は app.js のコメントに書かれた意図的な設計**で、
未保存判定が起動直後に誤発火しないようにするためのもの。
