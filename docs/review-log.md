# 批判レビューの記録

`docs/quality-gate.md` の合格判定に使った、実際に回したレビューの記録。
**何を、どの観点から、どう測って、何が出たか**を残す。出なかったことも残す —
「調べていない」と「調べたが出なかった」は違う。

## 方式

サブエージェントによる並行レビューを試みたが、この環境では起動したエージェントが
完了報告を返さなかった (最初の3体、絞り込み後の3体、診断用の最小タスク1体、
いずれも無応答)。**待ち続けても閉じないループより、閉じるループを選んだ。**

代わりに、観点ごとに独立した検証スクリプトを書き、**実プロセスとして同時に走らせた**。
各観点は別のブラウザインスタンスで動き、結果をファイルに残す。

## 観点A: アクセシビリティ / キーボード完結性

| 項目 | 結果 |
|---|---|
| 名前の無いボタン | なし (全ボタンにテキストか title) |
| Tab 到達可能な要素 | 35 |
| オーバーレイの tabindex | 0件。ただし矢印キーによる巡回を実装済みで、キーボードだけで全要素に到達できる |
| `<html lang>` | `ja` |
| ステータスバー | `rgb(139,148,158)` / 背景 `rgb(22,27,34)` / 11px |

**指摘なし。**

## 観点B: データ整合性 (同じ値で書き戻して内容が変わらないか)

21図種すべてでテンプレートをパースし、各要素のラベルを**同じ値で**書き戻して、
要素集合が変わらないことを確認。

- 20図種: OK (書き換え0件、要素集合が同一)
- kanban: 一度「★ 要素が変わった」と出たが、**検証スクリプト側の誤り**だった。
  `updateColumn(text, line, newName)` は第3引数が値なのに、スクリプトが汎用の
  `(text, line, field, value)` を仮定して `'label'` を渡していた。
  実機で列名を `Todo` → `作業待ち` に変えて意図どおり動くことを確認済み。

**実装の指摘なし。** ただし更新関数のシグネチャがモジュール間で揃っていない
(`updateColumn(text,line,value)` と `updateTaskField(text,line,field,value)`) のは
事実で、呼び出し側が間違えやすい。今回は誤検出だったが、将来の呼び出しミスの
温床にはなる。

## 観点C: 壊れた入力への堅牢性

8種の入力で pageerror が出ないことを確認。

| 入力 | status | pageerror |
|---|---|---|
| 空文字 | Error | なし |
| 空白だけ | Error | なし |
| 未知の図種 | Error | なし |
| 途中で切れた記法 | Error | なし |
| 5000文字の1ラベル | OK | なし |
| 制御文字 (NUL/BEL) | OK | なし |
| HTMLタグ入りラベル | Error | なし |
| 40段ネストの block | Error | なし |

**指摘なし。** status=Error は mermaid が拒否した表示であって、アプリは生きている。
どのケースでもプロパティパネルは描画され、エディタは操作可能なまま。

## 観点D: 性能回帰

| ノード数 | 流し込み→描画 | 1打鍵→反映 | overlay | 選択1回 | 矢印1回 |
|---|---|---|---|---|---|
| 20 | 56ms | 45ms | 21 | 83ms | 60ms |
| 60 | 90ms | 102ms | 61 | 83ms | 55ms |
| 120 | 159ms | 227ms | 121 | 68ms | 56ms |

**指摘なし。** 今回追加した処理 (オーバーレイの座標変換、選択の生存確認、
キーボード巡回) は要素数に対して線形で、120ノードでも体感を損なわない。

## 観点E: 自作コードへの敵対検証 (接続モード)

新しく書いたコードほど検証が薄いので、直前に実装した接続モードを標的に
3周のループを回した。詳細はコミット
`fix(connect): 自作の接続モードを自分で敵対検証して見つけた5件` に記録。

| 周 | 検出 |
|---|---|
| 1 | 図種切替でモードが残り別図に誤接続 / Escape で抜けられない / モード表示が無い |
| 2 | モード中に矢印キーで選択が動く / 始点を消しても線が引ける |
| 3 | 新規なし (収束) |

## 総括

実装に対する指摘は観点Eからのみ出た。A/C/D は問題なし、B は検証スクリプト側の
誤りだった。**「出なかった」を根拠にするために、何をどう測ったかを上に残している。**

# 第2ラウンド: 観点を増やす (2026-08-21)

6観点すべてが指摘0になった時点で「合格」を出したが、**0件は「その観点を見て
いない」でも出る**。ヘビーユーザ視点の8観点 (操作コスト / 発見可能性 / 一貫性 /
フィードバック / エラー回復 / 学習曲線 / スケール耐性 / ワークフロー適合) に対して
既存の6観点が見ていたのは実質3つだったので、見ていない側を足した。

## 追加した観点

| レビュアー | 観点 | 見るもの |

| r7-consistency | 一貫性 / 発見可能性 / エラー回復 | 21図種のプロパティ欄を横に並べ、同じ概念に同じ語・同じ操作が出ているか。削除が Undo 1回で戻るか |
| r8-scale | スケール耐性 | 100要素の図で、取りこぼし・末尾要素の選択・「押した要素が消えるか」・所要時間 |

## 見つかった欠陥

| # | 重大度 | 内容 |
|---|---|---|
| A22 | Critical | sequence の participant 削除が宣言行しか消さず、`A->>B` の参照が残るので**一覧から消えても図には残り続ける**。class / er / state を id 認識に直したとき sequence だけ取り残していた |
| A23 | Major | gantt だけプロパティ欄にタスク一覧が無く、タスクを選ぶ手段がチャート上のバーのみ。4件では困らないが100件では破綻し、一覧を持つ他20図種と揃わない |
| A24 | Minor | 一覧行の削除ボタン (✕) に title が無く、何が消えるか読み取れない。既定値が無かったので全21図種に効いていた |

A22 は既存の単体テストでは捕まらない。パーサは宣言行を見て「B は無い」と言い、
mermaid は参照を見て「B は在る」と言う — **同じ「存在する」に二つの述語**が
使われている、このセッションで何度も出たアーキタイプ。実描画でしか差が出ないので
オラクルに `expectAbsent` / `expectPresent` を足し、旧実装で FAIL することを確認した。
