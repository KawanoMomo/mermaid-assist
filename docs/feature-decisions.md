## 見送りの理由 (聞かれたときの回答)

**FEAT-002 図の直接編集がないのはなぜか**
21図種すべてで図とテキストの対応付けを持つ必要があり、単一HTMLで完結させる
方針と両立させるには規模が大きすぎる。現在はパネル経由の編集で全21図種を
等しく扱えており、**こちらの不足に関する指摘は65ラウンドで0件**。
競合にあることは採用理由にしない。

**FEAT-003 AI生成がないのはなぜか**
生成には図の内容を外部サービスへ送る必要がある。**本ツールは1枚のHTMLで
完結し、設計内容が外に出ないことを前提に作っている。** 秘密保持契約下の
設計資産を扱う用途で、この前提は譲れない。
白紙から書き始めるコストは21図種すべてのひな形で下げている (R63実測)。

**FEAT-006 共同編集がないのはなぜか**
サーバーが必要になり、単一HTMLでオフライン動作する前提が崩れる。
図は `.mmd` テキストなので、共同作業は Git の差分レビューで行える。

## 判断が要るもの

**FEAT-004 (UI-064, Major)**: 閉じたら作業が消える。
localStorage への退避自体は小さいが、**復元してよい条件の判定**が難しい。
A113/A114 (図種を切り替えても前の状態が残る) と同型で、
「別の文書を開いたのに前の内容が復活する」事故を作りやすい。

- 案A: 自動で復元する (事故リスクが最も高い)
- 案B: 「前回の続きがあります。開きますか」と確認してから復元する
- 案C: 復元しない (現状)

**製品の性格を決める判断なので測定では決まらない。判断を仰ぐ。**

## 決定: UI-064 (FEAT-004) は **案B — 確認してから復元する**

- **決定日**: 2026-08-23
- **決めた人**: Kawano Momo
- **PR #19**: マージ済み (2026-08-22 17:14:47Z / `943b307`)

3案のうち **案B** を採用:

| 案 | 内容 | 判断 |
|---|---|---|
| A | 自動で復元する | **不採用**。A113/A114 と同型で「別の文書を開いたのに前の内容が復活する」事故を作る |
| **B** | **「前回の続きがあります。開きますか」と確認してから復元する** | **採用** |
| C | 復元しない (現状維持) | 不採用 |

**実装時に守ること**:
- 確認を挟むので、**利用者が知らないうちに内容が入れ替わることはない**
- ひな形のまま (編集していない) なら復元を提案しない — 毎回聞かれると読まれなくなる
- 復元しなかった場合、退避した内容をいつ捨てるかを決める必要がある
  (捨てないと次回また聞かれる)

### UI-064: 確認してから復元する

「前回の続きがあります。開きますか」と聞いてから復元する。

**守ること**:
- 確認を挟むので、**知らないうちに内容が入れ替わることはない** (A113/A114 の事故型を避ける)
- ひな形のまま (編集していない) なら提案しない — 毎回聞かれると読まれなくなる
- 復元しなかった退避をいつ捨てるかを決める (捨てないと次回また聞かれる)

### FEAT-001: エディタに置換を付ける

本文全体を対象にした検索置換。**テキストがソースという本製品の構造と最も相性が良く**、
外部ライブラリも不要。実測で 15操作 → 2操作。

### UI-066: 図種+日付に統一

ひな形のタイトルを使わず、常に `<図種>-<日付>.mmd` にする。
**図種を切り替えたときの振る舞い (実測済) と規則が揃う**:

| | 現状 | 決定後 |
|---|---|---|
| 起動直後 | プロジェクト計画.mmd | **gantt-20260823.mmd** |
| 図種変更後 | sequenceDiagram-20260823.mmd | sequenceDiagram-20260823.mmd |

### UI-078: 図種で分ける

- **自己遷移が正当な図種** (stateDiagram 等): 線を引く
- **稀な図種** (flowchart 等): 「自分自身へは繋げません — 別の要素を選んでください
  (Escape で中止)」と告げ、**接続モードは続ける** (やり直し3クリックが不要になる)

### FEAT-903: 親の付け替えを実装候補へ

**実務で起きる**との回答。例: architecture-beta で `service ComM` を
アプリ層から BSW層へ移す。一覧で親を選び直せる UI を検討する。
静的解析では **12モジュールが parentId を持つのに付け替え経路は 0 件**。

**規模は M と見る**: 12モジュールで親の表現が異なる
(architecture の group / block の入れ子 / c4 の Boundary / mindmap のインデント)。
**1つずつ確かめてから作らないと、図種で不揃いになる型を踏む。**

## 決定の訂正: UI-078 は **全図種で自己ループを許す** (2026-08-23)

**最初の決定「図種で分ける」は、私の誤った説明を前提にしていた。**

私は「stateDiagram では自己遷移が正当、flowchart では稀」と説明したが、
**実測すると8図種すべてで mermaid が自己ループを描ける**:

| 図種 | 自分自身への線 |
|---|---|
| flowchart / stateDiagram / sequenceDiagram / classDiagram / erDiagram / requirementDiagram / block-beta / architecture-beta | **すべて描ける** |
| gitGraph | 描けない (記法上そもそも自己マージが無い) |

つまり**現状の GUI は、テキストで書けるものを黙って拒んでいた**。
これはこの製品が避けてきた「経路によって能力が違う」型そのもの。

**前提が崩れた決定をそのまま実装せず、報告して再判断を仰いだ。**
結果、**全図種で許す**に変更。

- 図種ごとの分類表が要らない → 図種が増えてもずれない
- 誤クリックで引いても Ctrl+Z で1回戻せる (実測)

## 決定: 批判ループは **案C — 観点を変えて回し続ける** (2026-08-23)

6ラウンドかけてお尋ねした「終了条件」への回答。**案C を採用。**

### なぜ観点を変える必要があるか

現在の8観点 (操作コスト / 発見可能性 / 一貫性 / フィードバック / エラー回復 /
学習曲線 / スケール耐性 / ワークフロー適合) は、**1人が1枚の図を編集する視点**に
固定されている。この視点での指摘は Minor まで下がり、直近は**検査器の欠陥
(通算12件) のほうが多く出ている**。

**「指摘が出ない」のは製品が完成したからではなく、同じ場所を測り続けているから** —
ラウンド64 で「欠陥は尽きた」と誤診し、測る場面を1つ変えただけで Major が出た
教訓 (`docs/coverage-map.md`) と同じ構図。

### 当てる順序 (まだ一度も測っていない視点)

| # | 視点 | 何が見えるか |
|---|---|---|
| **1** | **図を受け取る側 (レビュアー)** | 自分で描いていない図を読むときの摩擦。Git 差分・書き出し画像・命名 |
| 2 | 半年後の自分 | 当時の意図が図から読めるか。コメント・命名・構造の残り方 |
| 3 | 初めて触る同僚 | 説明なしでどこまで進めるか (現在は熟達者視点のみ) |
| 4 | 数十枚をまとめて扱う運用 | 1枚ではなく群として見たときの一貫性・命名衝突・横断検索 |
| 5 | 壊れ方の分類 | 「どう壊れるか」を体系的に。現在は個別の欠陥を潰しているだけ |

**視点1から当てる。** 現在のペルソナは「描く人」で、**受け取る人は一度も測っていない**。

### 視点を変えるときの規約

- **新しい視点で最初に出るのは「測っていないこと」の一覧**であって指摘ではない。
  `coverage-map.md` に足してから測る
- **前の視点で0件だったことを根拠に「良い」と言わない**。視点が違えば別の話
