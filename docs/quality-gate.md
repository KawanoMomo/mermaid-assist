# 合格基準 (Quality Gate)

このセッションの作業を「完了」と呼ぶための判定基準。曖昧な「だいたい直った」で
終わらせないために、**測れる形**で書く。

## なぜ必要だったか

471 unit + 269 e2e が全緑のまま、以下が残っていた:

- 一覧の ✕ が押した行と違う要素を削除する (block / flowchart)
- ID をリネームすると参照側が壊れる (6モジュール)
- 図をクリックしても選択できない (flowchart はオーバーレイがあるのに無反応)
- Undo が1キーストローク単位で、80文字打つと編集前に戻れなくなる

**テストが緑であること自体は合格の根拠にならない。** 何を測れば「壊れていない」と
言えるのかを先に決める。

## G1. テキスト変換の正しさ — 押した対象だけが変わる

GUI の1操作が DSL に与える変更は、**その操作が名指しした要素だけ**に閉じる。

| 判定 | 方法 |
|---|---|
| 押した要素が変わる | 操作前後の parse 結果を差分し、対象要素だけが変化 |
| 他の要素が変わらない | 同上。巻き添えがあれば FAIL |
| 前方一致で巻き込まない | `a` / `ab` / `abc` のように接頭辞を共有する id を必ずテストに含める |
| 同名ラベルで衝突しない | 同じラベルの要素を2つ持つケースを必ず含める |

## G2. 描画の正しさ — mermaid が実際に何を描くか

**`mermaid.parse` が通ることは合格の根拠にならない。** parse が通って render が
落ちる、両方通って図の意味だけ変わる、のどちらも実際に起きた。

`tests/render-oracle.js` で before/after を実ブラウザに描かせ、次を比較する:

- render が例外を出さないこと
- 描画されたテキスト (要素が増減していないか)
- gantt はバーの x/width (依存が切れて日付が飛んでいないか)

ケースごとに新しいページを開く。mermaid はダイアグラム種別ごとにモジュール
レベルの状態を持ち、同一ページで連続 render すると前のケースの id が漏れて
**「存在しない id を参照しているのに正しく解決される」偽の GREEN** が出る。

## G3. テストが同語反復でないこと — 変異で必ず落ちる

新しく書いたテストは、対応する実装を壊す変異を入れたら**必ず落ちる**こと。

最低限あてる変異:

- 修正した分岐を無効化する (`if (false)`)
- 完全一致を前方一致に緩める
- 対象範囲を広げる / 狭める
- ガードを外す

**生き残った変異はテストの穴として扱い、落ちるテストを追加する。**
「変異が意味を変えない」場合は死にコードなので実装から消す。

## G4. 画面の正しさ — 実機スクリーンショットを人が見る

自動テストの緑だけで GUI 変更を PASS にしない (ワークスペース CLAUDE.md の禁止事項)。

- Playwright で実際に描画し、**画像を開いて目視する**
- オーバーレイは可視化して、描画要素に重なっているか見る
- 数値 (幅・座標・フォントサイズ) も併記する。目視だけだと 6.8px と 10px の差を
  見落とす

## G5. 操作コストの回帰がないこと

ヘビーユーザーが1日に何百回も通る経路で、手数が増えていないこと。

| 経路 | 基準 |
|---|---|
| 要素を選ぶ | 図を直接クリックできる。キーボードでも移動できる |
| 1回の編集 | Undo 1回で戻る |
| 図種を切り替える | 切替直後に読めるサイズで表示される |
| 保存する | ファイル名が内容を識別できる |

## G6. スケール耐性

要素数が実務規模になっても破綻しない。

| 図種 | 規模 | 基準 (実測) |
|---|---|---|
| flowchart | 100ノード | render 208ms / 入力反映 190ms / エラー0 |
| gantt | 200タスク | render 68ms / 入力反映 65ms / エラー0 |

## G7. 権利

push する前に、他者の権利を侵害していないこと。

- 同梱した第三者コードのライセンス全文と著作権表示を再配布している
- リポジトリの LICENSE と package.json の license が一致している
- 履歴に第三者の著作物・個人情報が混入していない

## レビューの実施記録

判定の根拠にした実際のレビューは  に残す。
観点A (アクセシビリティ) / B (データ整合性) / C (堅牢性) / D (性能) を
独立プロセスとして並行実行し、観点E (自作コードへの敵対検証) は3周のループを
回して収束を確認した。

**「調べていない」と「調べたが出なかった」を区別する**ため、指摘が出なかった
観点についても何をどう測ったかを記録している。

## レビューの網羅について (2026-08-21 追加)

**「指摘0件」は、検査した範囲の外では何も意味しない。**

実測でこうなっていた。r11 (特殊文字) は更新関数の名前を表で持っており、
表に載っていない図種は静かに検査対象から外れていた。**21図種中6図種**しか
見ていない状態で「指摘0件」を報告していた。契約 (`operations.update`) で
呼ぶよう直したところ、**観点を1つも増やさずに47件**の指摘が出た。

そのため次を規約とする。

### 1. レビュアーは関数名の表を持たない

対象の選び方は契約 (ADR-012 `operations.{add,update,delete,moveUp,moveDown}`) に
寄せる。表は増えないので、モジュールが増えるほど検査は縮む。

### 2. UI 経路と契約経路の両方を確認する

同じ欠陥を UI 経路だけ直して契約経路を忘れる形が、これまでに8件出ている
(A54 / A56 / A57 / A58 / A60 / A62 / A63 / A64)。UI は生の更新関数を直接呼び、
契約経路は `operations.*` を通るので、**どちらか一方を直しても他方は古いまま残る**。

修正時は必ず両方を通して確認する。単体テストは契約経路 (`operations.*`) で書く。
UI 経路は e2e で押さえる。

### 3. 網羅率を機械で押さえる

`tools/review/lib.js` が各レビュアーの検査対象数を自動で数え、
`out/<name>.coverage.json` に書く。`coverage-floor.json` が下限で、
`gate.js` の `COV` 項目が下回りを FAIL にする。

下限を上げるのは自由。下げるにはファイルを書き換える必要があり、
その差分が「意図して範囲を狭めた」記録になる。

### 4. 検査から外れた組を黙って捨てない

「どの field でも本文が変わらず未検査」「mermaid 側の制限」といった
除外は件数を標準出力に出す。0件の内訳が見えないと、0件が網羅の証拠に見えてしまう。

### 5. 描けたことは正しいことの証拠にならない

mermaid は必ず例外を投げるわけではない。kanban の列名に括弧を入れると
parse は通り図も出るが、括弧の中だけが消える。描画に成功した場合も
`diagnose` を引き、名指しできる原因があれば警告帯を出す。

### 6. 測定条件も検査対象 (2026-08-21 追加)

UI-011 (パネルの収まり) は **観点が足りなかったのではなく、測る場所が実利用と
違っていた**ために見逃されていた。

| 測定条件 | 該当図種 |
|---|---|
| 1500x950 (当初) | 8/21 → Minor と判定 |
| **1366x768 (13インチのノートPC)** | **15/21** → Major |

実機を使うレビュアーの画面サイズは `VIEWPORT = { width: 1366, height: 768 }` で
固定する。13インチのノートPC が常用環境の最小で、ここで成立しないものは
「一部の利用者では成立しない」ではなく「多くの利用者で成立しない」。

**ただし条件を直すだけでは足りない。** 全観点を 1366x768 で走らせ直しても
0件のままだった。「画面に収まっているか」という述語がどこにも無かったからで、
条件の見直し (Y6) と述語の追加 (r21) は別の作業である。

### 7. 変異が入ったことを確かめる

r21 の変異注入で「検出できない」と見えた変異が、実は**ファイルに入っていなかった**
(CRLF のファイルに `\n` で置換していた)。
変異注入は「レビュアーが空振りでないこと」を確かめる手段だが、
**変異注入そのものが空振りしうる**。差分が入ったことを確認してから結論を出す。
